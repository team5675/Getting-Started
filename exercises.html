Robot Programming Practice

Try ten activities in order, starting at 0. Each one asks you to change or observe something, predict a result, and explain what happened. Work with a partner and take turns. You can revisit any activity whenever you need it.

Before the first activity

Use the stable 2026 tools and the starter version your mentor has checked. Activities use simulation first. The mentor guide lists the project setup checks.

Keep one branch through Activities 0–9. Commit and push after each activity; observation activities add a short learning note. Start a draft review at Activity 4 and keep updating it.

If you're stuck
  1. Say what you expected and what you observed.
  2. Check one thing: build output, simulation mode, controller input, or dashboard connection.
  3. Undo or correct the last small change and run again.
  4. After about five focused minutes, ask your partner or mentor. Bring the first relevant error or the log trace.

Read Robot Architecture when an activity points to a concept. You do not need to read the entire reference before starting.

0Get the code and save your first change

Files: README.md · Ideas: clone, branch, commit, push

Before you start: finish the Getting Started chapters and the simulated-light activity. Ask your mentor for the training repository URL and starting version. This website contains lessons; it is not the robot-code repository.

  1. Set up a GitHub account and ask your mentor for access to the training repository.
  2. In WPILib VS Code 2026, press Ctrl+Shift+P, choose Git: Clone, paste that URL, and select a local folder such as C:\dev. Open the cloned folder.
  3. Click the branch name at the bottom-left, choose Create new branch, and name it yourname/programming-practice. Use this same branch throughout Activities 0–9 so each activity keeps your earlier changes.
  4. In README.md, add your name to the programmers list. Open Source Control and click the changed file to inspect the diff: the lines you added or removed.
  5. Stage this file using +, enter a message such as Add Morgan to programmers list, and commit. Choose Publish Branch or Push to share it.
  6. Find your branch and commit on GitHub. The Git practice guide explains first-time setup and the review workflow.
Check your understanding

Show a partner your change online. Explain the difference between a commit (a local checkpoint) and a push (sharing those commits). A branch separates code history; it does not isolate a robot you deploy to.

1Run the simulator and observe a value

Files: learning-notes.md · Ideas: simulator input, enable, dashboard connection

Before you start: use the mentor-checked starter and its controller map. Start in simulation. Arrange any real-hardware testing separately with a mentor.

  1. Run WPILib: Simulate Robot Code. Let the build complete and select the Simulation GUI when prompted.
  2. In the simulator, assign your gamepad to the joystick port used by RobotContainer (often port 0; check the code). Move a stick and confirm the axis display changes. If you have no gamepad, ask for the mentor-tested keyboard joystick mapping.
  3. In the simulator's Robot State panel, select Teleoperated. Confirm it is enabled; some simulator versions combine mode and enable in one control. Return to Disabled when finished.
  4. Open AdvantageScope and use its simulator connection. Search the field tree for Drivetrain/Pose. Add it to the 2D field/odometry view and select the starter's field. The surrounding tree folders depend on whether you are connected live or reading a log.
  5. Plot Drivetrain/HeadingDeg and Template/Winner. Use the starter's A binding, then release it. Note what changes.

What you should see: the simulated pose changes as you drive, and the template's selected request changes when its binding runs. A blank dashboard is a connection or data question to investigate, not evidence that your Java is wrong.

Save and share: create learning-notes.md. Record one input you tried, the full log path you observed, and its result. Commit and push this note.

Check your understanding

Point to a specific value that proves an input reached the program. Explain the difference between starting the program, enabling teleop, and connecting the dashboard.

2Add and graph a counter

Files: TemplateSubsystem.java · Ideas: fields, periodic(), log values

Find TemplateSubsystem.java with Ctrl+P. Add the field below inside the class, outside its methods. Then add the two update lines inside its existing periodic() method; keep the existing code.

// Class field: created once for this subsystem object.
private int loopCount = 0;

// Add these two lines inside the existing periodic() method:
loopCount++;
Logger.recordOutput("Template/LoopCount", loopCount);

Keep the project's existing Logger import. If it is missing, the import is org.littletonrobotics.junction.Logger.

  1. Save and build. Read the first relevant build error if the build fails.
  2. Simulate, connect AdvantageScope, and graph Template/LoopCount.
  3. Predict the graph if you replace loopCount++ with loopCount += 2;. Make the change and run again.

What you should see: with the original update, the counter rises by about 50 per second in the standard 20 ms loop. With the new update, it rises about twice as fast.

Why does the field go outside periodic()?

A field keeps its value between method calls. A local declaration such as int loopCount = 0; inside periodic() creates and resets that local variable every call. The field resets when you restart the program, not every loop.

Save and share: commit and push your code. Describe which graph you expected and what you observed.

Check your understanding

Explain what changes the counter and what calls that code repeatedly. Predict the result if you move the declaration inside periodic(), then explain why that would be different.

3Trace two competing requests

Files: learning-notes.md · Ideas: requests, priority, command ownership

A request names a desired action. Arbitration means choosing which active request controls the output. First read the request section in Robot Architecture with your mentor.

The model below describes a request manager that retains both requests. It is different from two ordinary commands that each require the same subsystem: those commands interrupt one another. Your mentor will identify which behavior the starter implements.

InputRetained requests in this modelSelected request / example output
Hold ARUN_FORWARDRUN_FORWARD / 0.8
Keep A held; hold BRUN_FORWARD and PANIC_REVERSEPANIC_REVERSE / −1.0
Release B, keep A heldRUN_FORWARDRUN_FORWARD / 0.8
  1. Graph Template/ActiveRequests, Template/Winner, and Template/OutputPercent.
  2. Predict each step above, try it in simulation, and record the actual trace.
  3. If A disappears when B starts, inspect the commands' requirements with your mentor. An ordinary whileTrue binding does not automatically restart an interrupted A command while A stays held. Release and press A again to check.

Do not remove command requirements to make the trace match a diagram. Hardware ownership must remain explicit. The diagram describes a model; the trace tells you what your program did.

Save and share: record your prediction, result, and explanation in learning-notes.md. Commit and push.

Check your understanding

Explain whether A remained active while B ran, using the trace as evidence. If your prediction differed, describe what you learned about the starter’s command ownership.

4Add a request of your own

Files: TemplateRequest.java, RobotContainer.java · Ideas: enum, binding, priority

An enum is a list of named choices. In this starter, a request includes a priority and an output value. Check its constructor and arbitration method with your mentor before editing.

  1. In TemplateRequest, add this choice between RUN_FORWARD and HOLD. Keep the enum's commas and final semicolon:
SLOW_REVERSE(25, -0.3),
  1. In the existing RobotContainer.configureBindings(), add this binding if Y is unused:
driver.y().whileTrue(TemplateCommands.request(template, TemplateRequest.SLOW_REVERSE));

whileTrue starts the command when Y becomes pressed and cancels it when Y is released. It does not repeatedly restart an interrupted command.

  1. Predict Y alone, then Y+A, then Y+A+B using the ownership behavior you observed in Activity 3. Simulate and compare.
  2. In simulation only, change priority 25 to 75. If the starter has validateOrdering(), read its error when number and declaration order disagree. If arbitration compares numbers without that validation, predict which retained request now takes priority. Inspect the code to explain the result.
  3. Restore priority 25, build, and confirm the original behavior.

Save and share: commit and push the restored version. Open a draft pull request from your practice branch. Ask a teammate to review this change; keep the same branch and draft PR for the later activities.

Check your understanding

Explain how the starter decides priority and how you verified it. A corrected prediction with a clear explanation is useful progress.

5Give a waiting command a timeout

Files: TemplateCommands.java, RobotContainer.java · Ideas: command factories, completion, timeout

Use the starter's X binding and observe its timed action. With the demonstration sensor staying false, the expected RUN_FORWARD request lasts about two seconds and Template/TimeoutFired records the timeout.

A command factory is a method that creates a command. Copy runForwardUntilGoal into a new factory named holdBriefly(TemplateSubsystem s, double seconds). Change its request to HOLD and use seconds for the timeout. Preserve the cleanup and the warning that identifies a timeout.

In configureBindings(), add:

driver.povUp().onTrue(TemplateCommands.holdBriefly(template, 3.0));

onTrue starts the command once when the direction pad is pressed upward. It does not cancel the command simply because you release the direction pad.

  1. Predict the selected request after one second and after four seconds.
  2. Simulate and press POV-up once. Observe about three seconds of HOLD followed by cleanup and the timeout warning.
  3. Ask your mentor how to set the simulated goal sensor true. Verify early completion too; it should clean up without reporting a timeout.

Save and share: commit and push. Add both observed outcomes to your draft PR.

Check your understanding

Explain why a sensor-dependent action needs a timeout and where the request is removed when the command ends. Distinguish reaching the goal from running out of time.

6Measure distance to a field point

Files: CommandSwerveDrivetrain.java · Ideas: pose, meters, field coordinates

Pose2d represents an estimated position and heading; Translation2d represents an X/Y position. The estimate is useful, but it can be wrong.

For this 2026 baseline, use the blue-alliance field frame: X goes toward the red wall, and Y goes left when facing that wall from the blue side. Positions are in meters. Use the same frame on both alliances.

  1. In CommandSwerveDrivetrain.java, locate the existing periodic(). Keep its existing code. Ask your mentor to identify the project's already-loaded AprilTagFieldLayout; the example below calls it fieldLayout. If the drivetrain has no layout field yet, add a class field initialized once using the same season/layout selection as VisionSubsystem. Do not load a file every loop.
  2. Add the calculation inside that drivetrain method:
Translation2d center = new Translation2d(
        fieldLayout.getFieldLength() / 2.0,
        fieldLayout.getFieldWidth() / 2.0);
double distance = getState().Pose.getTranslation().getDistance(center);
Logger.recordOutput("Drivetrain/DistanceToCenterM", distance);

The geometry import is edu.wpi.first.math.geometry.Translation2d. This snippet uses getState() because it is inside the drivetrain class; it cannot be pasted unchanged into RobotContainer.

  1. Graph the result. Predict whether it increases or decreases as you drive toward the center, then away.
  2. Approach from a second direction. Try getting the estimated distance below 0.10 meters.

Save and share: commit and push. Record the units and one result in your notes.

Check your understanding

Explain why the distance shrinks when you approach the point from either direction. Explain why a small calculated distance does not, by itself, prove the real robot is at that point.

7Aim at a different point

Files: RobotContainer.java · Ideas: target position, heading, suppliers

Find the existing aim binding in configureBindings() and identify its button. Add this second binding in the same method if the right-stick button is unused:

// A practice coordinate in the 2026 blue-alliance field frame.
Translation2d myPoint = new Translation2d(2.0, 2.0);
driver.rightStick().whileTrue(
        aim.aimAt(myPoint, () -> -driver.getLeftY(), () -> -driver.getLeftX()));

() -> ... is a lambda: here it supplies a fresh joystick value whenever the command asks, rather than saving one reading during setup.

  1. Simulate and drive while holding the new binding. Check that the robot faces the selected point while moving. Observe Aim/IsAimed.
  2. Read Aiming in field coordinates. Explain why the same physical target needs the same field heading at the same robot pose on either alliance.
  3. Repeat with the simulator set to the other alliance. Separate driver-relative translation from field-relative heading in your explanation.

Optional challenge: choose a different target coordinate. Changing which point you aim at is different from adding an alliance-dependent offset to a heading. Use the project's approved target-selection helper if an alliance-specific point is needed.

Save and share: commit and push with a note describing both alliance checks.

Check your understanding

Point to the target coordinate and the code that sets the target-direction perspective. Explain what you tested instead of assuming a coordinate rule makes every future bug impossible.

8Run your command during an auto

Files: AutoRoutines.java and PathPlanner files · Ideas: named commands, deferred creation, events

Before you start: your branch must include holdBriefly from Activity 5. Ask your mentor for a working, simulated DriveOffLine auto; creating a first path is a separate lesson.

  1. Locate the starter's named-command registrations (in AutoRoutines, or the equivalent setup method). Add this registration alongside them, before the autos are built:
NamedCommands.registerCommand("HoldBriefly",
        Commands.defer(() -> TemplateCommands.holdBriefly(template, 1.0),
                Set.of(template)));

defer calls the factory when scheduled. Set.of(template) declares the required subsystem; it must cover the requirements of the command the factory returns. Use the existing imports for Commands and NamedCommands; Set is java.util.Set.

  1. Open the project in PathPlanner. Confirm the auto resets odometry to its starting pose. Add an event marker on its path that runs the named command HoldBriefly.
  2. Save the path and auto, rebuild, and simulate. Select DriveOffLine in the auto chooser before enabling Autonomous.
  3. Compare the field view with the request trace: HOLD should appear when the marker triggers.

Why the team uses defer: creating the inner command at scheduling time gives each use fresh command state. Keep this team convention for every named-command registration.

Save and share: commit the Java change and the changed files under src/main/deploy, then push.

Check your understanding

Explain the connection between the marker’s name, the registration, and the factory. Show evidence in the log that the event ran.

9Put it together: your first subsystem

Files: a new spinner package · Ideas: combine and explain your work

Create a simulated “widget spinner.” Give it a few actions, then use the logs to explain its behavior. This is practice for adapting a template to a new mechanism.

  1. Copy the template package to subsystems/spinner/. Rename its classes, filenames, package declarations, and references consistently: for example SpinnerRequest, SpinnerSubsystem, and SpinnerCommands.
  2. Design requests such as EJECT, SPIN, and NONE. Follow the arbitration and validation rules you verified in Activity 4.
  3. Include one action that ends on a simulated sensor or a timeout. Ensure it removes its request on normal completion and interruption.
  4. Construct one spinner instance in RobotContainer, bind two unused buttons, and log under Spinner/*.
  5. Ask a teammate to run your branch, use the controls, and inspect the traces. Each partner should explain one method and make one small change without the other person typing.

Save and share: commit and push, then mark your draft PR ready for review. Include what changed, how you tested it, and one question for your reviewer. Your mentor decides whether to merge into the training repository; a merge is not a score for your learning.

Optional next topic: position and speed control

These activities use fixed output values. A later mechanism may need feedback control to maintain a position or speed. Explore PID with a mentor when you need that behavior; it is not a prerequisite for this activity.

Check your understanding

Demonstrate an action, its completion or timeout, and cleanup. Explain which class would change when replacing the simulated hardware with a real device, and which behavior still needs testing on that device.
