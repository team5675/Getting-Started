FRC 5675 Getting Started Exercise Ladder Robot Architecture

The Exercise Ladder

Ten rungs, 0 through 9, in order, each one page. Every exercise changes (or observes) the real robot code and ends with something you can see on a dashboard — no toy programs. Work in pairs. Simulation counts: everything here runs on a laptop with Simulate Robot Code if the practice bot is busy. By rung 9 you'll have built a new subsystem the same way you will in January.

The Git ritual (set up in Exercise 0, details in docs/github-guide.md): every exercise starts on a fresh branch named yourname/exercise-N and ends with a commit and push — that push is your "done." From Exercise 4 on, done means a pull request a teammate or mentor has reviewed. Code that only exists on your laptop doesn't exist.

Companion reading: a few rungs below link to lessons from Code with Kate's "Intro to Programming for FRC Teams" (2026) — read the linked lesson before that rung, not instead of it. Two caveats: that site also has older course editions built around IntelliJ, not our WPILib VS Code — if a lesson mentions IntelliJ, skip it, it's not ours. And its PhotonVision lesson describes a different vendor stack (a separate coprocessor + USB cameras) than our Limelight 4 setup — interesting background, but don't use it as a reference for VisionSubsystem.java.

0Get the code, own a branch

Files touched: none yet · New ideas: clone, branch, commit, push

Read first: Installing WPILib and VS Code and Where to Find Help (Code with Kate) — what WPILib actually is, and the four places to look before you ask a mentor.
  1. Make a GitHub account (school email is fine) and get added to the team5675 organization by a mentor.
  2. In WPILib VS Code: Ctrl+Shift+P → Git: Clone → paste the repo URL → pick a folder. You now have the team's entire code history on your laptop.
  3. Open the Source Control panel (the branching-lines icon on the left). Click the branch name in the bottom-left corner → Create new branch → name it yourname/exercise-0. You are now working on a copy that can't hurt anyone.
  4. Prove the pipeline: open README.md and add your name to a "Programmers" list at the bottom (start the list if you're first). In Source Control: the file appears under Changes — click it to see the diff (green = added). Stage it (+), write the message Add <name> to programmers list, click Commit, then Publish/Sync to push.
  5. Open the repo on github.com, find your branch, and look at your commit — that exact diff, with your name on it, forever in the history.
You win when: your commit is visible on github.com and you can answer: what's the difference between committing and pushing? (One is a local save point; one shares it.)
Why this matters: during build season, "whose laptop has the working code?" has ended more shop nights than any bug. The answer is now always the same: GitHub has it, with the history of how it got that way.

1Deploy, drive, and watch the robot think

Files touched: none · New ideas: deploy loop, AdvantageScope, log keys

  1. Open the project in WPILib VS Code. Press Ctrl+Shift+P → Simulate Robot Code (or Deploy, if you have the practice bot).
  2. Open AdvantageScope → Connect to Simulator (or to the robot).
  3. In the left tree, expand RealOutputs/Drivetrain. Drag Pose onto an Odometry view. Attach a gamepad/keyboard in the sim GUI and drive.
  4. Now find and plot Drivetrain/HeadingDeg and Template/Winner. Press the A button. Watch the winner change.
You win when: you can drive the ghost robot around the field view AND point at the exact log key that proves the A button does something.

2Your first log line

Files touched: TemplateSubsystem.java · New ideas: periodic(), editing real code safely

The template subsystem's periodic() runs 50 times a second. Add a loop counter to it and publish it:

// Near the top of the class, with the other fields:
private int loopCount = 0;

// Inside periodic(), anywhere:
loopCount++;
Logger.recordOutput("Template/LoopCount", loopCount);
  1. Build. Fix any red squiggles before deploying (read the message — it names the file and line).
  2. Simulate/deploy, then find Template/LoopCount in AdvantageScope and plot it.
You win when: you see a perfectly straight line climbing by 50 every second — you just watched the scheduler's heartbeat. Ship it: commit on yourname/exercise-2 and push — your first code change in the team's history.
Why this matters: "add a number, log it, look at it" is 80% of real robot debugging. You now know the whole loop: edit → build → run → observe.

3Watch an argument get settled

Files touched: none · New ideas: requests, arbitration, priority

Two commands are about to want the same subsystem at the same time. Old code fights; ours arbitrates. Open AdvantageScope and watch Template/ActiveRequests, Template/Winner, and Template/OutputPercent side by side, then:

  1. Hold A. → active: [RUN_FORWARD], winner RUN_FORWARD, output 0.8.
  2. Keep holding A, also hold B. → active shows both; winner flips to PANIC_REVERSE, output -1.0.
  3. Release B only. → winner falls back to RUN_FORWARD — not to off. Nobody had to remember to restart it.
You win when: you can narrate step 3 to a teammate: why did the output become 0.8 and not 0.0 when B was released?

4Add a rung to the ladder

Files touched: TemplateRequest.java, RobotContainer.java · New ideas: enums, the ordering contract

  1. In TemplateRequest, add a new request between RUN_FORWARD and HOLD: 
    SLOW_REVERSE(25, -0.3),
  2. In RobotContainer.configureBindings(), bind it: 
    driver.y().whileTrue(TemplateCommands.request(template, TemplateRequest.SLOW_REVERSE));
  3. Run it. Hold Y alone; then Y+A; then Y+A+B. Predict each winner before you look.
  4. Now break it on purpose: change SLOW_REVERSE's priority number to 75 (leaving it declared below RUN_FORWARD's 50) and run again. Read the crash message carefully — the robot refused to start and told you exactly which two lines disagree. Fix it back.
You win when: all three predictions were right, and you saw validateOrdering() catch your deliberate bug at boot instead of at a match. Ship it: commit (the fixed version!), push, and open your first pull request — a teammate reviews the diff before it merges. From here on, every exercise ends with a reviewed PR.
Why this matters: in 2026 a request enum carried priority numbers that nothing actually read. Code that looks like it means something it doesn't will eventually fool someone — so this codebase checks itself.

5Never wait forever

Files touched: TemplateCommands.java, RobotContainer.java · New ideas: command factories, race, timeouts

Press X and watch Template/Winner: RUN_FORWARD holds for exactly 2 seconds, then stops, and Template/TimeoutFired appears in the log. The "sensor" (isAtGoal()) never fired — the timeout saved us.

Now build your own version. In TemplateCommands, copy runForwardUntilGoal into a new factory holdBriefly(TemplateSubsystem s, double seconds) that requests HOLD and gives up after seconds. Bind it:

driver.povUp().onTrue(TemplateCommands.holdBriefly(template, 3.0));
You win when: POV-up produces 3 s of HOLD and your own timeout warning in the log. Ship it: PR it — and in the description, explain in one sentence why the timeout exists. PR descriptions are where you practice explaining code.
Why this matters: a 2026 auto once waited on a sensor that never answered — and ate the rest of the auto. Every hardware wait in this codebase races a timeout. Every one you ever write should too.

6Where am I? (pose math)

Files touched: RobotContainer.java or a subsystem · New ideas: Pose2d, Translation2d, field frame

Read first: WPILib Swerve Classes (Code with Kate) — the full API surface of Pose2d, Translation2d, and ChassisSpeeds. You've been calling these since Exercise 1; this is where you get fluent in them.

The robot always knows its field pose: drivetrain.getState().Pose. Field frame means: origin at the blue corner, X toward the red wall, Y left, in meters — always, for everyone, on both alliances.

  1. Somewhere that runs every loop (the drivetrain's periodic() is fine), compute and log the straight-line distance to field center: 
    Translation2d center = new Translation2d(
        fieldLayout.getFieldLength() / 2.0, fieldLayout.getFieldWidth() / 2.0);
double dist = getState().Pose.getTranslation().getDistance(center);
Logger.recordOutput("Drivetrain/DistanceToCenterM", dist);
    (You'll need an AprilTagFieldLayout — copy how VisionSubsystem loads one.)
  2. Drive around the sim field watching the number. Park exactly on the center mark: can you get it under 0.10?
You win when: the number shrinks as you approach center from any direction — proof it's geometry, not guesswork.
Why this matters: "distance from my pose to a field point" is the seed of every auto-aim, auto-align, and shoot-on-the-move feature you'll write in January.

7Aim somewhere new

Files touched: RobotContainer.java · New ideas: field points, aim command, alliance mirroring

Left bumper already aims at field center. Add a second aim point of your own:

// A made-up target 2 m in from the blue corner:
Translation2d myPoint = new Translation2d(2.0, 2.0);
driver.rightStick().whileTrue(
        aim.aimAt(myPoint, () -> -driver.getLeftY(), () -> -driver.getLeftX()));
  1. Drive around holding the binding — the robot should keep its nose on that spot while you strafe circles around it. Watch Aim/IsAimed flicker true.
  2. Question to answer out loud (check section 5 of the teaching guide): where in this code is the red-alliance 180° handled? Trick question — find who handles it for us, and why there's no if (red) anywhere.
  3. Bonus: wrap your point in FieldPointAim.flipIfRed(myPoint) and explain what that changes — and what kind of alliance logic it is (data-level: choosing which point; never angle math).
You win when: the robot orbits your point nose-in, and you can explain to a mentor why this bug can't come back on red alliance.

8Hook a command into an auto

Files touched: AutoRoutines.java + PathPlanner GUI · New ideas: named commands, defer, event markers, resetOdom

  1. In AutoRoutines, register your exercise-5 command as a named command — copy the defer pattern exactly: 
    NamedCommands.registerCommand("HoldBriefly",
        Commands.defer(() -> TemplateCommands.holdBriefly(template, 1.0),
                Set.of(template)));
  2. In the PathPlanner desktop app, open the DriveOffLine auto (make it if it's missing — the code has been alerting about it). Confirm Reset Odometry is on for the start. Add an event marker mid-path that triggers HoldBriefly.
  3. Simulate: select the auto in the chooser, run autonomous, and watch Template/Winner flip to HOLD right as the ghost robot crosses your marker.
You win when: the log shows your command firing mid-path — you just built the exact mechanism autos will use to score in 2027.
Why defer, always: registering a bare new command hands PathPlanner ONE shared object; reuse the name twice and the scheduler chokes on it. defer makes a fresh command every trigger. 2026 learned this the annoying way. We don't relearn it.
Optional enrichment: Choreo: Physics-Based Path Planning (Code with Kate) — a different trajectory tool some teams use instead of PathPlanner. We've already committed to PathPlanner; read this as "why we didn't pick Choreo," not a live decision.

9Graduation: build a subsystem from the template

Files touched: new package! · New ideas: everything above, combined — this is the January skill

Read first: WPILib PIDController (Code with Kate). The template's requests are just fixed percentages on purpose — real 2027 mechanisms will need a PID loop to hold a position or a velocity, and this is the class for it. Nothing in this exercise requires PID yet, but January will.

Invent a fake mechanism (a "widget spinner"). Build it exactly the way you'll build the real 2027 mechanisms:

  1. Make subsystems/spinner/. Copy TemplateRequest → SpinnerRequest and TemplateSubsystem → SpinnerSubsystem (fix packages/names — the compiler will point at every spot you miss).
  2. Design its request menu: at least EJECT (top priority), SPIN, NONE. Choose priorities; keep declaration order = priority order — validateOrdering() is watching.
  3. Make SpinnerCommands with a request(...) factory and one timeout-guarded action.
  4. Construct it in RobotContainer, bind two buttons, log under Spinner/*.
  5. Demo to a mentor: buttons, arbitration, fallback, logs. Then answer: "In January this spinner becomes an intake with a real motor. Which class changes, and which classes don't?" (Hint: look at the IO seam at the bottom of the template.)
You win when: a teammate can operate your subsystem from your dashboard traces alone — and your pull request is merged into main after a real review: the reviewer ran your branch, pressed your buttons, and asked at least one question you had to answer with a code change or a comment. Merged means you can add a game mechanism to this robot without a mentor driving the keyboard. That's the whole point of the fall.
