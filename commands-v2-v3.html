Commands v2 and v3: what changes?

Keep the same behavior in mind while comparing two ways to describe it.

All lessons · Home Java

One idea to remember

A command describes an action and declares which hardware it controls. Both frameworks coordinate actions so conflicting requests do not control the same hardware at once. SystemCore does not require Commands v3.

The current course and reviewed 2027Practice code use Commands v2. WPILib says v2 and v3 will remain supported side by side for several seasons. Official framework overview. They are supported choices, not two packages to install together: Alpha 7 explicitly rejects mixing their vendordeps.

1. Compare the shape of an action

QuestionCommands v2Commands v3
Where does behavior live?Often lifecycle methods: initialize, execute, isFinished, end; or small factory commands composed together.Often one coroutine-backed function that reads in the order actions happen.
How does it let other work run?Each execute call returns promptly; the scheduler calls it again.A coroutine pauses cooperatively at a yield or a framework wait; it resumes later.
What represents owned hardware?Subsystem requirements.Mechanism requirements; ownership and composition rules differ.
Does the new version remove the need to stop safely?No: cleanup belongs in the appropriate end behavior, including interruption.No: normal completion and cancellation need explicit, tested cleanup.

See the official migration discussion. A coroutine is a function that can pause and resume; it is not permission to block the whole robot with an ordinary busy loop.

2. Describe the same light exercise

This is a behavior sketch, not Java to paste:

Turn the practice light on.
Keep it on for one second while other robot work continues.
Turn it off when finished.
If canceled early, also turn it off.

In Lesson 8’s v2 implementation, the scheduler manages the command’s lifetime and its timeout. A v3 implementation can express the wait inside its action body. Both must release control while waiting and both need the early-cancel case. The v3 introduction explains cooperative execution.

3. Should beginners learn both immediately?

No. Learn Java, actions, requirements, timeouts, interruption and cleanup first. Use v2 to read the team’s actual code. Read this comparison after the first command lesson; do not maintain two versions of every exercise.

V3 may eventually make longer behavior easier to read because ordinary loops and local variables fit naturally in the action. That is worth a mentor-led experiment, particularly before writing many new mechanisms. It is a separate design choice from the SystemCore hardware transition.

4. Mentor decision before changing the team project

The reviewed practice project explicitly selects CommandsV2 and its vendordep rejects installing CommandsV3 alongside it. Its drivetrain and PathPlanner command integration use v2 types. The inspected PathPlanner 2027 AutoBuilder source at October 4 also uses v2. That integration is not a drop-in v3 migration; it does not predict what a later release will support. Replacing only a JSON file is not a migration.

In a separate experimental project, test the same light action in both versions: normal finish, early cancel, Disable, a competing command, and a timeout. Then verify the exact CTRE, PathPlanner and logging integration intended for the robot, including cleanup when an auto is interrupted. Keep executable v3 examples pinned to a checked release; current documentation can move ahead of an installed alpha.

Pause and explain

Why is v3 optional? What lets another command run while this one waits? Why is “it works when it finishes normally” not a complete test?
