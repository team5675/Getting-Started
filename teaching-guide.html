1. The big picture

This project is a chassis that runs: you can deploy it, pick up a controller, and drive a swerve robot that continuously knows its position on the field. There are deliberately no game mechanisms — no intake, no shooter — because the 2027 game doesn't exist yet. What exists is everything a game mechanism will need to stand on.

Three ideas organize everything you'll read below:

One owner per fact. The drivetrain owns the pose. The Constants camera array owns the camera list. CanSeam owns how CAN buses are made. RobotIdentity owns which robot we're on. When a fact lives in exactly one place, changing it is one edit — and it can't disagree with itself.

Failures should be loud. A robot that silently does the wrong thing is worse than one that visibly breaks. That's why placeholder practice-bot calibration is obviously wrong (all zeros, giant banner) instead of subtly wrong, why every health problem raises a named alert, and why timeouts log a warning when they fire.

2026 already paid for these lessons. Twelve specific bugs from last season's code review are designed out of this baseline — not patched, but made structurally hard to reintroduce. Section 10 has the full scorecard.

2. Command-based in five minutes

WPILib's command-based framework has two main characters:

A Subsystem is a chunk of hardware and the code that owns it — the drivetrain, a future intake. Each subsystem has a periodic() method that runs automatically every 20 ms, always, no matter what else is happening. That's where monitoring and logging live.

A Command is a thing the robot does for a while — "drive with the sticks," "aim at that point," "run the auto." Commands have a tiny lifecycle: initialize() once at start, execute() every 20 ms, isFinished() asked every cycle, end() once at the end. The scheduler (run from Robot.robotPeriodic()) is the referee: it watches buttons, starts and stops commands, and enforces one rule —

The requirements rule Every command declares which subsystems it requires. Two commands that require the same subsystem can never run at once; scheduling the second interrupts the first. This is how "hold right bumper to aim" cleanly takes the drivetrain away from normal driving and hands it back on release. A command that forgets to declare a requirement opts out of this protection — that was 2026 bug 2.10, and you'll see addRequirements(...) called religiously in every command here.

One more player: the default command. Each subsystem may have one command that runs whenever nothing else claims it. The drivetrain's default command is "drive with the joysticks" — which is why the robot is drivable the moment it boots.

3. Driving: from stick to swerve module Drivetrain/*

Push the left stick and, 20 ms later, eight motors are doing coordinated math. Here's the whole journey:

Field-centric means "stick up" always drives away from your own alliance wall, regardless of which way the robot's nose points — the robot subtracts its own heading (from the pose estimate!) before doing wheel math. This is why driving gets weird when the pose is wrong, and why the vision section matters to drivers, not just programmers.

2026 lesson · the one-sided clamp Slow mode in 2026 used Math.max(input, -limit) to cap stick input. Look carefully: that only limits one direction. Pushed the other way, the stick was never capped at all — slow mode half-worked, all season, and nobody noticed in the shop because you naturally test driving forward. JoystickUtil now uses MathUtil.clamp(v, -limit, +limit) — a floor and a ceiling — and processes X and Y together as one 2D vector so diagonals and deadband behave the same in every direction. When you write any limiter: always ask "what happens with a negative input?"
Try it Deploy, then in AdvantageScope plot Drivetrain/ModuleStates on the Swerve tab while someone wiggles the sticks (robot on blocks!). You will literally watch the request pipeline think. Hold left bumper and watch every speed scale down — in both directions.

4. Vision: how the robot knows where it is Vision/*

The drivetrain counts wheel rotations to track position ("odometry"). Wheels slip; tiny errors add up; two minutes into a match, pure odometry can be off by a meter. The fix: cameras that recognize AprilTags — barcodes bolted to the field at known coordinates — and calculate the robot's position from them. Fusing "wheels say we moved this much" with "camera says we're exactly here" is the whole game.

The Limelight offers two ways to get a pose, and the difference between them is the key to the entire design:

MegaTag1MegaTag2
Needs to be told our heading?No — solves position and heading from tag geometry aloneYes — you feed it the robot's heading every frame
QualityTrustworthy from a cold boot, but noisy at rangeVery stable position — if the heading you fed it was right
Failure modeJitterGarbage in, confident garbage out
Our useSeed: once, at startupMaintain: every frame after seeding

Three details worth understanding deeply:

Heading is gyro territory. Once seeded, vision is only allowed to correct X and Y — its rotation estimate is fed to the filter with a gigantic uncertainty (9999999), which is Kalman-filter language for "ignore this." The Pigeon's heading barely drifts in a match, while vision heading jitters; letting them fight made 2026's pose shimmy.

Every disable clears the seed. Robot.disabledInit() calls clearPoseSeeded(), and re-seeding restarts automatically. Fresh enable, fresh lock — never trust drift you accumulated before sitting still.

The camera list is one array. Constants.VisionConstants.kCompCameras holds a name and mounting position per camera. The subsystem loops over whatever is there — adding a fourth camera at kickoff is one line, and its mounting offsets are pushed to the Limelight automatically at boot.

2026 lesson · the lopsided field fence 2026's "is this pose possible?" filter checked y < 0.5 || x < 0.5 || x > 17 — three edges of a four-edged field, with margins that pointed inward. Result: no filtering at all past one sideline, and legitimate poses rejected whenever the robot legally hugged a wall (exactly where autos start!). The rewritten isOnField() bounds both ends of both axes symmetrically, with a small margin pointing outward, and reads field dimensions from WPILib's official tag layout so they update themselves at 2027 kickoff. The lesson generalizes: when you write a boundary check, draw the rectangle on paper and check all four lines.
Try it Set the robot on the floor near a printed AprilTag, open AdvantageScope's Odometry tab, and add Drivetrain/Pose. Watch Vision/SeedStatus flip from WAITING_FOR_VISION to OK from limelight-… [MT1]. Then cover the camera: the pose keeps moving on odometry alone. Uncover it and watch vision pull it back. That tug is the fusion working.

5. Aiming without the red-alliance bug Aim/*

Also standalone This section is also its own page — aiming.html — for linking directly to it from elsewhere (that's what Exercise 7 does).

FieldPointAim does one generic thing: while the driver keeps translating, it continuously rotates the robot to face a chosen point on the field. When the 2027 game is revealed, "the point" becomes the goal / feeder / whatever — the pattern doesn't change.

The interesting part is what's missing: there is no if (alliance == Red) anywhere in the file. That absence is the design.

2026 lesson · the 180° aim bug 2026's aiming worked all season… until the first red-alliance match, where it pointed exactly backwards. Why: the swerve request layer already flips joystick translation for red (that's "operator perspective"), but the aiming code also did its own red/blue flip on the target heading. One value was in field-language, one in driver-language; comparing them was correct on blue and 180° wrong on red. Testing happened on blue. The categorical fix is a rule, not a patch: do all math in blue-alliance field coordinates, and let alliance enter in exactly one place.

Here, that one place is the request itself. Phoenix 6 (26.3.0+) lets a FieldCentricFacingAngle request be told its target direction is blue-frame:

// The ONE place alliance is handled — CTRE flips for red internally.
new SwerveRequest.FieldCentricFacingAngle()
    .withTargetDirectionPerspective(ForwardPerspectiveValue.BlueAlliance);

// Everything else is pure blue-frame geometry — no ifs:
Rotation2d headingToTarget = targetPoint.minus(robotPose.getTranslation()).getAngle();

Translation stays operator-perspective (the driver's stick feels normal), heading is closed-loop locked to a field-frame direction, and there is nothing for a future edit to get backwards. PathPlanner follows the same rule — its one flip point is the supplier passed to AutoBuilder.configure, and the health check reuses PathPlanner's own FlippingUtil instead of hand-rolling a mirror.

6. The request pattern Template/*

The subsystems/template/ folder is a complete, working demonstration of the team's request-based state manager — the pattern every real 2027 mechanism will copy. It "drives" a pretend motor so you can play with it today (hold A and B on the controller and watch Template/CurrentRequest).

The problem it solves: two commands both want the same mechanism. The driver holds a button to run an intake fast; an automation wants it slow in the background. If both write motor power directly, last-writer-wins, and when the driver's command ends and zeroes the motor, it stomps the automation that still wanted it.

The pattern: commands never touch hardware. They add a request when they start and remove it when they end. The subsystem keeps the set of active requests and, whenever it changes, applies the highest-priority one.

2026 lesson · the priority field nobody read 2026's request enums carried priority numbers — and the arbitration loop never looked at them. It walked declaration order, which merely happened to agree. Any student rearranging the enum for readability would have silently changed robot behavior. Now arbitrate() explicitly sorts by the field: max(Comparator.comparingInt(r -> r.priority)) — one source of truth, and the comparator line is the policy, readable in plain sight. If a codebase carries two ways to express the same rule, delete one.

TemplateActionCommand demonstrates two more habits in twenty lines: the request is removed in end() even when interrupted (so requests never leak), and isFinished() pairs its sensor condition with a timeout that logs a warning when it fires — because in an auto, a command waiting forever on a broken sensor eats the whole autonomous period (2026 bug 2.6).

7. Logging & dashboards — your X-ray vision Logger.recordOutput

You cannot ssh into a robot mid-match. Logging is how the robot testifies about what happened — and on this baseline, logging is not an afterthought bolted on with SmartDashboard.putNumber calls. (In fact, SmartDashboard appears nowhere in this codebase: it is removed from WPILib in 2027, and 2026's habit of using it live while the "real" logging sat commented out is exactly what we're not repeating.)

Every interesting value flows through one call — Logger.recordOutput("Some/Key", value) — and AdvantageKit fans it out to two destinations at once:

Dashboards as a learning tool

Here's the suggested way to use the two dashboards — not just as displays, but as how new programmers build intuition:

Elastic is the match dashboard. Keep it boring and glanceable: the Alerts widget (every health check reports there by name), the auto chooser, battery voltage, Vision/SeedStatus. Drive team sees green or they see a named problem. Build the layout together once and save it with the code.

AdvantageScope is the engineering microscope. A great standing exercise for every new programmer, in order: (1) Odometry tab — add Drivetrain/Pose, push the robot by hand, watch it move on the field map; (2) add Vision/OdometryOnlyPose in a second color and watch the two separate as wheels slip; (3) Swerve tab with Drivetrain/ModuleStates vs ModuleTargets — commanded vs actual, the daily driver for "why does it drive weird"; (4) Line graph of Power/BatteryVoltage during hard driving — learn what brownout looks like before it costs a match. Each exercise is ten minutes and permanently upgrades what a student can debug.

Rule of thumb: when you write a feature, decide its log keys in the same commit. If you can't name what you'd want to see on a graph when it misbehaves, you're not done designing it.

The team's WPILOG Analyzer The team's own Unified WPILOG Analyzer (the HTML tool in the project knowledge) reads exactly the files this robot writes. Feed it a match .wpilog and point its pose sources at Drivetrain/Pose (the fused track) and Vision/OdometryOnlyPose (the shadow track that never gets vision corrections). The gap between those two lines is wheel drift — the robot keeps both on purpose, anchored to the same seed, precisely so that comparison stays meaningful. Heat maps of Power/ChannelPeaks answer "what browned us out" without guessing.

8. Power, health checks, and the pre-auto routine Health/*

Two subsystems watch the robot so humans don't have to remember to:

PowerMonitor tracks battery voltage, total and per-channel current, per-channel peaks across the match, and amp-hours — with alerts at warning and critical thresholds. One structural detail matters beyond power:

2026 lesson · the phantom device new PowerDistribution(...) "succeeds" even when no such device is on the CAN bus — you just get an object whose channels all read zero. 2026 wrapped the constructor in try/catch and believed it. The 2027 rule: constructing a hardware object proves nothing; demand proof of life. PowerMonitor only marks the device real after it reports a plausible battery voltage (>4 V) for ten straight cycles; otherwise a named alert says it's missing and its readings are skipped, not trusted. The same principle explains why the health check tests that the gyro's data is fresh, not merely that the gyro is "connected."

SystemHealthCheck runs the automated half of the pre-match checklist, every cycle, while disabled — which is exactly the window when the robot sits on the field before a match. Each check raises its own narrowly-named alert ("limelight-back not responding", not "something's wrong"), because a stressed pit crew needs a destination, not a mood. It verifies: every expected CAN device answers (missing ones listed by name), gyro data fresh, every camera's heartbeat beating, battery match-safe, a real auto selected, and deployed constants matching the physical robot.

The pre-auto startup routine

The last two checks are the 2027 addition: before auto ever starts, the robot compares its live fused pose against the selected auto's starting pose (read from the PathPlanner file, mirrored via PathPlanner's own utility on red). More than 0.5 m off, or facing more than 15° wrong, and an alert names the auto and the error size. Setup stops being a guess:

Alerts panel, robot sitting on the field:
✓ CAN devices OK          ✓ Cameras OK           ✓ Gyro fresh
✓ Vision seeded (MT1)     ✓ Battery 12.7 V
⚠ Robot 0.82 m from 'CenterTwoPiece' start position
→ slide the robot until the warning clears. Then play.

Notice the quiet bonus: this check can only pass if the entire vision pipeline — cameras, seeding, filtering, fusion — is alive. Green light on positioning is a green light on localization.

9. The SystemCore seams (2027 migration map) ★ SEAM ★

In January 2027, FRC replaces the roboRIO with SystemCore — the biggest control-system change in the program's history. This baseline is built on the current stable toolchain so it deploys to real hardware today, and every place the migration will touch is fenced behind one access point with a ★ SYSTEMCORE MIGRATION SEAM ★ banner comment. The migration plan is: practice bot first, and only the seams change.

The bench that validates this Every belief in the table below is being tested for real, ahead of kickoff, on a Raspberry Pi 5 SystemCore stand-in — see the SystemCore Clone Bench guide (or the raw markdown source) for the build, the open questions, and a running findings log (including whether Commands v2 or v3 wins, and what actually broke when the analyzer met real 2027 timestamps).

Until then, everything here builds and drives on the hardware the team actually owns. Grep for SYSTEMCORE MIGRATION SEAM to see every site.

11. Kickoff day: how to extend this

January 2027, game reveal weekend. Here's the play:

1. Mechanisms. Copy subsystems/template/ per mechanism. Rename the enum to the mechanism's requests, put real motors in the subsystem constructor (via CanSeam, never a raw bus string), real sensor reads in the command's isFinished() — keeping the timeout. Delete the template's demo bindings from RobotContainer once real ones exist.

2. Field points. Add the game's aim-worthy coordinates to FieldConstants (blue-frame, always). FieldPointAim works immediately; bind buttons that call setTargetPoint.

3. Cameras. Re-measure mounts on the 2027 chassis, update the one array in Constants. Done.

4. Autos. Draw paths in the PathPlanner GUI (enable Reset Odometry on every start pose), register real named commands — deferred, like the placeholder shows. New autos appear in the chooser by themselves, and the pre-auto positioning check starts verifying your lineup automatically.

5. Field dimensions. Install 2027 WPILib; the tag layout — and with it the vision bounds and field constants — updates itself. Verify once.

6. SystemCore. When (and only when) the stable 2027 toolchain ships: practice bot first, seams only. Section 9 is the map.

The chassis runs. It knows where it is. Everything else is January's problem — and now you know exactly where January's code will go.
