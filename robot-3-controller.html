1. What a controller sends

Every pass of the loop, the robot can ask the controller for its axes and buttons. Each stick has two axes, and each axis reads from −1.0 to 1.0. A button reads true or false.

The driver wantsStick readingRobot direction
Go forward (away from the driver)left Y is negativeforward = -leftY
Slide leftleft X is negativeleft = -leftX
Turn counter-clockwise (to the left)right X is negativeturn = -rightX; counter-clockwise is positive in WPILib

2. Clean up the numbers

A stick may not rest at exactly 0. It might sit at 0.03 even when nobody touches it, and the robot would creep. A deadband treats any reading close to 0 as exactly 0.

A simple deadband has a problem: just outside it, the output jumps from 0 to 0.08. WPILib’s MathUtil.applyDeadband rescales instead, so the output grows smoothly from 0 and still reaches 1.0 at full stick. Then many teams square the result, keeping its sign. Small pushes become gentler for fine control, while full stick stays full speed.

Where this goes: add the import near the top of Robot.java. Then replace only your practice() method.

Code to use: import

import edu.wpi.first.math.MathUtil;

Code to use: practice()

private void practice() {
    double[] rawValues = {0.03, 0.08, 0.10, 0.50, -0.50, 1.00};
    for (double raw : rawValues) {
        double clean = MathUtil.applyDeadband(raw, 0.08);
        double curved = Math.copySign(clean * clean, clean);
        double speed = curved * 4.0; // pretend top speed: 4.0 m/s
        System.out.println("raw " + String.format("%5.2f", raw)
            + "  clean " + String.format("%6.3f", clean)
            + "  curved " + String.format("%6.3f", curved)
            + "  speed " + String.format("%5.2f", speed) + " m/s");
    }
}

String.format("%5.2f", raw) prints a number with 2 decimals, padded to 5 characters wide so the columns line up. Math.copySign(a, b) gives a with the sign of b, so squaring −0.457 gives −0.208, not +0.208.

Look at the 0.10 row: the deadband passes a tiny 0.022, and squaring makes it about 0.00047, which rounds to 0.000 at three decimal places. Half stick gives 0.83 m/s, not 2.0. That leaves plenty of fine control in the first half of the stick.

3. Read your browser input repeatedly

The keyboard lab uses the screen's directions: W is up (+Y), D right (+X), S down (−Y), and A left (−X). Those keys express field directions directly. They are not raw Xbox axis readings, so do not add the stick sign flips from section 1 to this code.

Where this goes: add the counter field inside Robot, outside its methods. Add this teleopPeriodic method alongside robotPeriodic; leave robotPeriodic and its scheduler unchanged.

private int controllerPrintCount = 0;

@Override
public void teleopPeriodic() {
    controllerPrintCount++;
    if (controllerPrintCount % 25 == 0) {
        var input = container.input();
        System.out.println("screen right / field X: " + input.x()
            + "  screen up / field Y: " + input.y());
    }
}
  1. Save, restart with .\gradlew.bat simulateJava, and open the browser station.
  2. Choose Teleop and click its keyboard area. Hold D, then W, then A, then S.
  3. Read the Terminal afterward. Changing windows disables the model; select Teleop again to continue.

Expect D to produce X = 1 and Y = 0; W gives X = 0 and Y = 1. A and S produce the corresponding negatives. With no key held both values are zero. The model will not move until you connect its default command in Lab 2. Turning the model does not rotate these screen-oriented controls.

A real stick provides continuous values between −1 and 1 and may drift near zero. The keyboard gives discrete −1/0/+1 values, so use the calculation in section 2 to explore deadband and curved response.

4. Try one variation

In section 2, change the deadband from 0.08 to 0.15. Predict which rows change before you run.

Hint and expected result

Rows 0.03, 0.08 and 0.10 are now all inside the deadband, so all three print 0.000. The 0.50 row becomes (0.50 − 0.15) / 0.85 = 0.412, so curved 0.170 and speed 0.68 m/s. Full stick still gives 4.00. A bigger deadband ignores more stick drift but makes the robot less responsive to small pushes.

In the real robot · 2027Practice

Source map and exact reviewed versions · Private team repository; excerpts remain readable here.

The practice bot turns the right stick into a turning speed in one short method. It uses WPILib’s versions of the two steps you just tried:

Reading example from src/main/java/frc/robot/util/JoystickUtil.java — do not paste

public static double rotation(
    CommandXboxController controller, double deadband, double curveExponent) {
  double value = MathUtil.applyDeadband(-controller.getRightX(), deadband);
  return MathUtil.copyDirectionPow(value, curveExponent);
}

And where the sticks are read every loop, in RobotContainer.java — do not paste

drivetrain.setDefaultCommand(
    drivetrain
        .applyRequest(
            () -> {
              boolean slow = slowModeButton.getAsBoolean();
              double[] t = stickTranslation(slow);
              return fieldCentric
                  .withVelocityX(t[0])
                  .withVelocityY(t[1])
                  .withRotationalRate(stickRotation(slow));
            })
        .withName("Drive (field-centric)"));

In the first excerpt, -controller.getRightX() flips the sign so that pushing right turns clockwise, which is negative in WPILib. MathUtil.copyDirectionPow(value, 2.0) squares the value and keeps its sign. It does the same job as your Math.copySign.

The second excerpt is the robot’s default drive command. The part starting with () -> { is a lambda: a small method with no name, handed to the drivetrain. The drivetrain calls it on every pass of the loop. So the sticks are read fresh 50 times a second, never just once.
