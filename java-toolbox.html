Build on a class: extends and @Override

A subclass reuses the parent class’s contract and can provide a more specific method. @Override lets the compiler check that your method really replaces an inherited one. A spelling mistake should fail during compilation rather than silently creating an unused callback.

public class InheritancePractice {
    static class Sensor { int readValue() { return 0; } }
    static class SimSensor extends Sensor {
        @Override int readValue() { return 7; }
    }
    public static void main(String[] args) {
        Sensor sensor = new SimSensor();
        System.out.println(sensor.readValue()); // 7, using the subclass behavior.
    }
}

Try it in InheritancePractice.java

Change SimSensor.readValue to return 9 and predict the output. Misspell its method with @Override still present, compile, then repair it. In the robot project, KeepLightOn extends Command and overrides initialize/end; Robot extends LoggedRobot and overrides periodic/mode callbacks.

Ask now: lambdas, suppliers and method references

A lambda is a short unnamed function. () -> controls.value means “read this when asked,” not “remember the number now.” A supplier is an object whose get method provides a value. A method reference such as controls::show names an existing method that can be called later.

public class LambdaPractice {
    static class Controls {
        double value = 1.0;
        void show() { System.out.println(value); }
    }
    public static void main(String[] args) {
        Controls controls = new Controls();
        java.util.function.DoubleSupplier live = () -> controls.value;
        System.out.println(live.getAsDouble()); // 1.0
        controls.value = 2.0;
        System.out.println(live.getAsDouble()); // 2.0
        Runnable display = controls::show;
        display.run(); // 2.0
    }
}

Try it in LambdaPractice.java

Replace the supplier body with 0.0, run, then restore the live field reading. Explain why a controller command needs fresh input each cycle. A command factory creates a command when called; Commands.defer asks a factory at scheduling time. Its requirement set must match what the returned command uses.

Name the choices: enum and switch

An enum lists the permitted named choices. A switch selects the behavior for one choice. Meaningful names make it harder to confuse a mode with an arbitrary number. This is a plain-Java example, not a new robot framework.

public class StatePractice {
    enum Mode { DISABLED, MANUAL, AUTO }
    static String describe(Mode mode) {
        switch (mode) {
            case DISABLED: return "Stopped";
            case MANUAL: return "Driver input";
            case AUTO: return "Scheduled path";
            default: throw new IllegalArgumentException("Unknown mode");
        }
    }
    public static void main(String[] args) {
        System.out.println(describe(Mode.DISABLED));
        System.out.println(describe(Mode.MANUAL));
        System.out.println(describe(Mode.AUTO));
    }
}

Try it in StatePractice.java

Change one label and run. Add a fourth practice enum choice and a matching case; explain what happens if you omit its case. The real robot’s request/state choices can use enums too. For telemetry, explain which state was chosen rather than logging only an unexplained integer.

A result might be absent: Optional

Optional represents either a present value or an absent result. Absence is not the same thing as a measured zero. Check presence before get; calling get on an empty Optional throws an exception.

public class OptionalPractice {
    static String describe(java.util.Optional<Double> meters) {
        if (meters.isPresent()) {
            return "Observed: " + meters.get();
        }
        return "No observation: keep estimate";
    }
    public static void main(String[] args) {
        System.out.println(describe(java.util.Optional.of(2.0)));
        System.out.println(describe(java.util.Optional.of(0.0)));
        System.out.println(describe(java.util.Optional.empty()));
    }
}

Try it in OptionalPractice.java

Run all three cases and explain why zero and missing data must stay distinct. Do not invent a zero pose when a camera provides no valid observation. The training path loader uses getStartingHolonomicPose().orElseThrow(): our supplied path must have a start, and a missing one is a setup error to report.
