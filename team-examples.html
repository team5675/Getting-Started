1. Give useful choices names

Before this reading: variables, methods, and objects (Lessons 3, 5, and 7).

Imagine telling a teammate to use a slower driving setting. Saying “use SLOW” is easier to remember than saying “use 0.15 for both numbers.” The team grouped these choices in an enum named DriveSpeeds. An enum defines a fixed set of named choices. This one also stores values with each choice.

2026 source: src/main/java/frc/robot/subsystems/DriveSpeeds.java, lines 4–9. Exact excerpt; surrounding code is omitted.

Reading example — do not paste into your sandbox

    // Defaults
    FULL(1.0, 1.0),
    HALF(0.5, 0.5),
    SLOW(0.15, 0.15),
    X_ONLY(1.0, 0.0),
    Y_ONLY(0.0, 1.0),

Walk through HALF

  1. // Defaults is a comment. Java ignores the text after // on that line.
  2. HALF is one choice’s name. Capital letters help distinguish these named constants.
  3. (0.5, 0.5) passes two decimal values to the enum’s constructor: its setup code. The first becomes xMax; the second becomes yMax.
  4. The comma between the numbers separates the two inputs. The comma after the closing parenthesis separates this entry from the next entry.
  5. The surrounding enum declaration and constructor are outside this short excerpt. This is why pasting just these lines into Robot.java would not make a complete program.

For this reading, think of X and Y as two directions of driving. The numbers are stored settings for limits; the code that uses them determines their effect. 0.5 is one half, or 50%, but this excerpt alone does not tell you a measured speed in meters per second.

2. Ask an object for one stored value

Before this reading: the previous reading and the two objects in Lesson 7.

The practice counter’s getCount() returned a stored number. The real drive-speed choices have a similar method, getXMax(). A method whose main job is to return a value is often called a getter.

2026 source: src/main/java/frc/robot/subsystems/DriveSpeeds.java, lines 27–33. Exact excerpt; surrounding code is omitted.

Reading example — do not paste into your sandbox

    private final double xMax;
    private final double yMax;
    private final double rotationMax;

    public double getXMax() {
        return xMax;
    }
PieceWhat it means here
privateThe field is accessed directly inside this enum’s class, not directly by unrelated classes.
finalThe field is assigned once. Here the constructor supplies its value.
double xMaxA field named xMax holding a decimal-capable number.
public double getXMax()Other code can call this method. It takes no inputs and returns a double.
return xMax;Give the caller the value stored in this object’s xMax field, then leave the method.

Follow one call from left to right

Consider DriveSpeeds.HALF.getXMax():

  1. DriveSpeeds identifies the enum.
  2. .HALF selects its HALF choice. Its constructor stored 0.5 as xMax.
  3. .getXMax() calls the getter on that choice. The empty parentheses mean no argument is needed.
  4. return xMax; hands 0.5 back to the caller. It does not change the stored value.

Returning is different from printing. This getter does not display anything. The caller could print its result, store it in a variable, or use it in a calculation. It also does not command a motor by itself.

Your turn: predict two results

What would DriveSpeeds.SLOW.getXMax() return? What would DriveSpeeds.Y_ONLY.getXMax() return?

Hint: connect the field to the constructor input

Both calls ask for X, so read the first number in each entry from reading 1.

Check the two results

SLOW returns 0.15. Y_ONLY returns 0.0. Selecting a different choice changes which object supplies the value; the getter’s instructions are the same.

3. Give the scheduler its next turn

Before this reading: Lesson 8, including starting and stopping the pretend light.

A command class describes an action. Something still has to arrange when that action starts, runs, and ends. WPILib’s scheduler does that coordinating work. This short method in last year’s Robot.java gives it a turn during each robot loop.

2026 source: src/main/java/frc/robot/Robot.java, lines 22–25. Exact excerpt; surrounding code is omitted.

Reading example — do not paste into your sandbox

  @Override
  public void robotPeriodic() {
    CommandScheduler.getInstance().run(); 
  }

Unpack the two layers

  1. @Override says this method supplies the behavior for a method defined by the parent class.
  2. public void robotPeriodic() defines a method called robotPeriodic. It takes no arguments and returns no result value.
  3. WPILib calls that method repeatedly. It is different from the robotInit() examples that run once at startup.
  4. CommandScheduler.getInstance() gets the shared scheduler object. You do not create another scheduler with new.
  5. .run() calls that object’s run method. It handles scheduled commands and subsystem periodic work.

Check your explanation

No. The class describes an action; a command object must be created and scheduled for it to run. The scheduler then manages its lifecycle. Keeping the scheduler call in Robot.java is part of making that framework work.

4. Start requests, then remove them

Before this reading: Lesson 8’s initialize/end pair and the scheduler reading above.

The pretend light turned on at the beginning and off at the end. Last year’s SpinIntake command followed a related pattern: ask three mechanisms to do something, then remove those requests when the command ends.

A request here is a named desired behavior stored by a subsystem. Adding it asks the subsystem to consider that behavior; it does not necessarily set a motor output on this line. Other code chooses among active requests.

2026 source: src/main/java/frc/robot/subsystems/Intake/SpinIntake.java, lines 21–27. Exact excerpt; surrounding code is omitted.

Reading example — do not paste into your sandbox

  @Override
  public void initialize() {
    // intake.isIntaking = true;
    intake.addIntakeRequest(IntakeRequest.INTAKE);
    indexer.addIndexerRequest(IndexerRequest.INTAKE);
    shooter.addFeederRequest(FeederRequest.REVERSE);
  }

Read the first active instruction

intake.addIntakeRequest(IntakeRequest.INTAKE);

  1. intake refers to an object representing one mechanism.
  2. The dot selects a method on that object: addIntakeRequest.
  3. The parentheses contain the input: IntakeRequest.INTAKE, a named choice from an enum.
  4. The semicolon finishes the statement. This line asks the intake subsystem to add the INTAKE request.
  5. The next two lines make similar requests on indexer and shooter. You can recognize the pattern without knowing their internal motor code.

initialize() runs once when this command starts. The commented line beginning // is a historical note; it does not run. Now look for the matching cleanup:

2026 source: src/main/java/frc/robot/subsystems/Intake/SpinIntake.java, lines 32–39. Exact excerpt; surrounding code is omitted.

Reading example — do not paste into your sandbox

  @Override
  public void end(boolean interrupted) {
    intake.removeIntakeRequest(IntakeRequest.INTAKE);
    indexer.removeIndexerRequest(IndexerRequest.INTAKE);
    // indexer.addRequest(IndexerRequest.IDLE_AGITATE);
    shooter.removeFeederRequest(FeederRequest.REVERSE);
    // intake.isIntaking = false;
  }
When the command startsWhen the command endsSame request to match

indexer.addIndexerRequestindexer.removeIndexerRequestIndexerRequest.INTAKE
shooter.addFeederRequestshooter.removeFeederRequestFeederRequest.REVERSE

end(boolean interrupted) receives a true-or-false value telling whether the command was interrupted. This method removes all three requests regardless of that value. Both the object and the request must match the addition.

Trace a start and a stop

  1. The command starts: its initialize method adds three requests.
  2. Subsystem code considers those active requests as the robot loop repeats.
  3. The command ends or is canceled: end removes those requests.
  4. Each subsystem’s remaining requests and fallback behavior determine what it does next. Removal alone does not prove its motor is stopped.

Your turn: find a missing cleanup

If the shooter.removeFeederRequest(...) line were missing, which request would this command fail to remove? Would deleting a line beginning // have the same effect?

Hint: match the third row

Find the request inside the parentheses of the shooter addition. Comments are ignored by Java.

Check your explanation

The command would fail to remove FeederRequest.REVERSE from shooter. That request could remain active. Deleting a commented-out line changes no executed instruction, so it would not have the same effect.

For mentors: design details outside this beginner reading

The historical SpinIntake constructor has addRequirements(intake) commented out. Do not treat that as the beginner rule for new hardware commands. The intake selector walks enum declaration order, rather than reading stored numeric priority. Its EnumSet records request types, not individual owners; two sources adding the same request type can interfere when one removes it. Review ownership, arbitration, duplicate requests, and cleanup before reusing this design.
