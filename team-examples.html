Small pieces of team code you can read, predict, and explain.

Recognize the ideas in your team's code

These short excerpts come from last year's team and its final 2026 robot code. Read them after the matching beginner chapter. They are examples to trace, not complete files to paste into your sandbox.

2026 reference: the historical robot used a different stack from the planned teaching baseline. These snippets are not a SystemCore port. Keep student practice on WPILib 2026.

1. Give useful values names

After the variables chapter, look at these entries from DriveSpeeds. An enum groups named choices; these entries each supply two numbers to a constructor.

2026 source: src/main/java/frc/robot/subsystems/DriveSpeeds.java, lines 4–9. Exact excerpt; surrounding code is omitted.

    // Defaults
    FULL(1.0, 1.0),
    HALF(0.5, 0.5),
    SLOW(0.15, 0.15),
    X_ONLY(1.0, 0.0),
    Y_ONLY(0.0, 1.0),

FULL, HALF, and SLOW communicate intent. Here the numbers are stored settings for X and Y limits; their eventual effect depends on the code that reads and applies them. The names alone do not prove the robot's actual speed.

Explain it: which entry has an X value of 1.0 and a Y value of 0.0? Why is a name easier to discuss with a teammate than an unexplained pair of numbers?

2. A method returns a stored value

After the methods chapter, compare the field and its getter:

2026 source: src/main/java/frc/robot/subsystems/DriveSpeeds.java, lines 27–33. Exact excerpt; surrounding code is omitted.

    private final double xMax;
    private final double yMax;
    private final double rotationMax;

    public double getXMax() {
        return xMax;
    }

private keeps access to the field inside this class. The public method returns its value. The constructor, outside this excerpt, initializes the final field. A call to DriveSpeeds.HALF.getXMax() returns 0.5.

Try it: trace which value DriveSpeeds.SLOW.getXMax() returns. Explain what return does; this method does not command a motor by itself.

3. Connect the scheduler to the robot loop

After the command chapter, find the repeated scheduler call in the team's actual Robot.java:

2026 source: src/main/java/frc/robot/Robot.java, lines 22–25. Exact excerpt; surrounding code is omitted.

  @Override
  public void robotPeriodic() {
    CommandScheduler.getInstance().run(); 
  }

WPILib calls robotPeriodic(). This method then runs the command scheduler, which manages command lifecycles and subsystem periodic calls. It is the link between the repeated robot loop and the commands you have been reading.

Explain it: why does defining a command class alone not make its action happen?

4. Start a request, then clean it up

After trying the simulated-light command, read how SpinIntake starts requests for three 2026 mechanisms:

2026 source: src/main/java/frc/robot/subsystems/Intake/SpinIntake.java, lines 21–27. Exact excerpt; surrounding code is omitted.

  @Override
  public void initialize() {
    // intake.isIntaking = true;
    intake.addIntakeRequest(IntakeRequest.INTAKE);
    indexer.addIndexerRequest(IndexerRequest.INTAKE);
    shooter.addFeederRequest(FeederRequest.REVERSE);
  }

2026 source: src/main/java/frc/robot/subsystems/Intake/SpinIntake.java, lines 32–39. Exact excerpt; surrounding code is omitted.

  @Override
  public void end(boolean interrupted) {
    intake.removeIntakeRequest(IntakeRequest.INTAKE);
    indexer.removeIndexerRequest(IndexerRequest.INTAKE);
    // indexer.addRequest(IndexerRequest.IDLE_AGITATE);
    shooter.removeFeederRequest(FeederRequest.REVERSE);
    // intake.isIntaking = false;
  }

Pair each add... call with its remove... call. Cleanup runs when the command ends, including interruption. The commented-out lines are historical notes, not statements Java executes. You do not need to understand all three mechanisms to trace the start/cleanup pairs.

Explain it: what request might remain active if one matching removal were missing?
Mentor note: what not to copy automatically

The supplied SpinIntake constructor has addRequirements(intake) commented out. That is a historical ownership choice, not the beginner rule for new hardware commands. The intake selector in this archive walks enum declaration order rather than reading the stored numeric priority. Its EnumSet also records request types, not individual request owners. If two sources add the same type, removing one can clear it for both. Resolve ownership, duplicate requests, and cleanup before using this design as a new template. Keep that design review separate from these short reading exercises.
