Save and share your work

A first walkthrough of Git, with a mentor nearby and one small change to follow.

A step to do with a mentor

Git helps a team keep a history of changes and review each other’s work. This is the only step on the route that needs a mentor, a training repository and an account.

Before you begin: get the training repository URL, permission to access it, and the starting branch or version from your mentor. You also need Git installed and, for sharing, a GitHub account with access. Do not guess which repository to use.

No training repository yet?

That is fine. Do this instead, then keep going:

  1. Stop the simulator and make a backup copy of your sim-starter folder.
  2. Press Next at the bottom of this page to go on to the next step. It keeps using the same sim-starter folder you have used since Lab 1.
  3. Come back to this page when your mentor has the repository ready. The capstone reminds you.
Your lab work stays where it is

Cloning downloads a separate project into a new folder. It does not contain your sim-starter edits. When you finish this page, use File → Open Folder to reopen your own sim-starter folder before you continue. Moving your own work into the training repository is a different job: ask your mentor before copying any files across.

1. Understand the four different actions

ActionWhat it doesWhere it happens
SaveWrites the text you edited into a file.Your computer.
CommitRecords selected file changes as a named checkpoint in Git history.Your local repository.
PushUploads your commits to the shared repository.From your computer to GitHub.
Pull requestProposes your branch’s changes for someone to review.On GitHub; opening one does not merge it.

A repository is a project tracked by Git. A branch is a named line of work within it. For these cumulative activities, keep one practice branch rather than starting over for every activity.

2. Get a local copy

  1. Open the WPILib VS Code version that matches your mentor’s training repository and press Ctrl+Shift+P.
  2. Choose Git: Clone. Paste the training URL your mentor provided.
  3. Choose a local parent folder such as C:\dev. Cloning downloads a copy into a project folder.
  4. Choose Open when prompted. Confirm you see the expected project files. If a trust prompt appears, check with your mentor that this is the intended team repository.
  5. Confirm the starting branch/version with your mentor before making changes. Build and run the unmodified starter once using its instructions.

If you already cloned this training repository, use File → Open Folder to open that existing copy instead.

3. Create your practice branch

  1. Find the current branch name in the lower-left status bar. Click it.
  2. Choose Create new branch and enter a name such as alex/programming-practice, using your own name.
  3. Confirm that the status bar now shows that new branch name.

A branch does not create a new folder. You keep editing in the same project folder. Check the branch name before each session.

4. Make one small checkpoint

  1. Make one intended lesson change, or write an observation in learning-notes.md. Save the file.
  2. Run the relevant simulation check if you changed code. Write the actual result, including an unresolved problem if there is one.
  3. Open Source Control from the left activity bar (or press Ctrl+Shift+G).
  4. Click a changed file. The diff shows what changed. Read the added and removed lines; confirm they are yours.
  5. Click the + beside each intended file to stage it. Staging selects changes for the next commit. Review only those files under Staged Changes.
  6. Enter a short message such as Explain the counter prediction and result, then click Commit.
  7. Confirm the intended changes no longer appear as uncommitted changes. The checkpoint now exists locally.

If Git asks for your name or email, ask a mentor to help set your chosen commit identity. A GitHub-provided private commit email can be used.

5. Share and verify

  1. For the first push, choose Publish Branch if shown. For later commits, use Git: Push from the command palette.
  2. If prompted, follow the GitHub sign-in flow. Ask for access help if needed; do not put a password or token in a project file.
  3. Open the training repository on GitHub. Use its branch selector to choose your practice branch.
  4. Find your commit message and open the changed file. Confirm you can see the new text online.

Pause and explain: if you saved and committed but did not push, where is your new checkpoint? It is still on your computer.

6. Ask for review when the activity calls for it

For the later team-project activities, open one draft pull request at Activity 4. Continue pushing to that same branch; the pull request updates. At Activity 9, mark it ready for review.

  1. On GitHub, open Pull requests → New pull request.
  2. Choose the mentor’s destination branch as the base and your practice branch as the compare branch. Read the file changes.
  3. Use the dropdown beside Create pull request to choose Create draft pull request. Explain what changed, how you checked it, and one question you have.
  4. Share the review link with your mentor using the team’s usual process. Let the mentor decide when and whether to merge the practice work.

When the screen does not match

I do not see Git commands or a branch

Check that Git is installed and that you opened the cloned repository folder. A folder with Java files is not automatically a Git repository. Ask a mentor before initializing or publishing a new repository.

There are hundreds of changed files

Pause before staging. The project may need its ignore rules checked. Build output, .gradle, robot logs, passwords, and tokens do not belong in your commit.

Push was rejected, or Git reports a conflict

Keep your work and ask a mentor to help reconcile the changes. Do not force-push or discard files to make the error disappear.

I staged the wrong file

Use the minus control beside that file under Staged Changes to unstage it. Unstaging keeps your edits; it only removes them from the next commit’s selection.

Your first review milestone

In the mentor’s training repository, make one tested change, inspect the diff, commit, push and open a draft pull request. Explain expected versus observed behavior. A reviewer should check the explanation, changed files and test evidence. The website itself cannot grant repository access.
