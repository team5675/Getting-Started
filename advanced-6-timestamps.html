When was that picture taken?

Every camera picture is a little old when it arrives. Use its time stamp so the robot blends it in at the right moment.

Today’s small goal

Work out when a camera picture was really taken, show why that time matters for a moving robot, and spot a time stamp in the wrong units.

1. Every picture arrives late

Between the moment a camera takes a picture and the moment the robot code reads the result, time passes. The camera exposes the picture, finds the tags, solves for the pose and sends it over the network. This delay is the latency, often a few tens of milliseconds.

How much does that matter? It depends on how fast the robot is moving. The code below prints a small table using two arrays and a loop inside a loop.

Where this goes: in Robot.java in your practice project, replace only robotInit().

Code to use

@Override
public void robotInit() {
    double[] speeds = {1.0, 3.0, 4.7};          // meters per second
    double[] latencies = {0.020, 0.035, 0.100}; // seconds
    for (double speed : speeds) {
        for (double latency : latencies) {
            double behindCm = speed * latency * 100.0;
            System.out.println(speed + " m/s, " + String.format("%.0f", latency * 1000)
                + " ms late: " + String.format("%.1f", behindCm) + " cm behind");
        }
    }
}

At full speed with 100 ms of latency, the picture shows the robot almost half a meter behind where it really is. If the code pretended the picture was taken “now”, every camera fix would pull the robot backward.

2. The fix: a time stamp

Each result needs a capture-time estimate in the estimator’s clock. For the Limelight botpose arrays used here, robot code derives that estimate from the NetworkTables sample timestamp minus the camera’s reported capture-plus-processing latency. The array is not already stamped with its exposure time. The pose estimator keeps about 1.5 seconds of odometry history. When a fix arrives, it looks up where odometry said the robot was at the picture’s time, applies the correction there, and replays the wheel movements since then.

That is why addVisionMeasurement on the previous page needed a time as well as a pose. The time must be right, and that is where things go wrong.

3. Work out the time, and catch a units mistake

For this arithmetic exercise, pretend the sample timestamp is its arrival time and ignore network delay. In real code, use the timestamp attached to that sample (converted to the local clock), not the time the robot loop happens to read it. The camera reports its capture-plus-processing latency. Our approximation is:

picture time = time received − latency, with both in the same unit: seconds.

Where this goes: replace only robotInit() again.

Code to use

@Override
public void robotInit() {
    long receivedMicros = 12_345_678; // when the robot received the packet, in MICROseconds
    double latencyMs = 35.0;          // how old the camera says the picture already was
    double now = 12.360;              // the robot's clock right now, in seconds

    double pictureTime = receivedMicros / 1_000_000.0 - latencyMs / 1000.0;
    System.out.println("Picture taken at " + String.format("%.4f", pictureTime) + " s");
    System.out.println("Age: " + String.format("%.4f", now - pictureTime) + " s");

    // The same moment written in NANOseconds, but divided as if it were microseconds
    long receivedNanos = 12_345_678_000L;
    double wrongTime = receivedNanos / 1_000_000.0 - latencyMs / 1000.0;
    System.out.println("Wrong units: age " + String.format("%.1f", now - wrongTime) + " s");
}

Expected output — read this; do not paste it into Java

Picture taken at 12.3107 s
Age: 0.0493 s
Wrong units: age -12333.3 s
PieceWhat it does here
longA whole-number type for very big numbers. 12 billion doesn’t fit in an int.
1_000_000.0Dividing by a decimal keeps the decimal part. The underscores are only for reading.
12_345_678_000LThe L says “this is a long.”

The last line is the dangerous one. A time in the wrong unit doesn’t crash anything; it just produces a nonsense age, here about 12,000 seconds “in the future”. In WPILib 2026, NetworkTables records times in microseconds. The 2027 version the practice bot runs records them in nanoseconds, 1000 times smaller units. Code that divides by the wrong number is off by a factor of 1000.

4. Check every picture’s age

This practice project accepts ages from −0.05 to 0.5 seconds. Those are chosen limits, not universal camera rules. The small future tolerance allows clock jitter; a larger error can mean wrong units, unsynchronized clocks, network delay or stale data. Passing this range check alone does not prove correct timing.

Where this goes: in the same robotInit(), after the "Age: " line and before the comment about nanoseconds.

Code to use

double age = now - pictureTime;
if (age < -0.05) {
    System.out.println("Problem: picture time is in the future");
} else if (age > 0.5) {
    System.out.println("Problem: picture is too old");
} else {
    System.out.println("Age OK");
}

This project rejects a 0.6-second-old picture because it exceeds the chosen 0.5-second limit. A correctly timed older observation can still help an estimator if it lies within its history; motion itself is why latency compensation exists.

5. Which clock?

A time stamp is only useful if it comes from the same clock as the pose estimator it goes into. On a 2026 robot there are two clocks: the roboRIO’s clock, and the one CTRE’s Phoenix library uses for its swerve code. CTRE’s generated 2026 drivetrain converts camera times from one to the other before blending them. The alpha-7 practice project assumes compatible clock epochs on SystemCore. Its age check detects large discrepancies but cannot prove synchronization: a small, consistent offset can still pass. Verify the installed versions with measured packet ages and motion tests before changing conversions.

How a clock problem looks on the dashboard

On the practice bot, a picture with an impossible age raises the vision.timestamp alert, and the Pre-Match tab’s Camera row turns red with “picture times don’t match the robot clock”. Before October 2026 this check only ran after the pose was seeded, and seeding needed good times. So a clock problem showed up only as “waiting for vision”, forever. The reviewed branch checks new pictures before seeding. A follow-up fix gives the two streams separate verdicts; its status is recorded below.

In the real robot · 2027Practice

The practice bot checks every new picture’s age with a small method, whether or not the pose is seeded yet. It uses the same limits as your check:

Reading example from src/main/java/frc/robot/subsystems/vision/VisionSubsystem.java — do not paste

static String packetAgeProblem(double ageSeconds) {
  if (!Double.isFinite(ageSeconds)) {
    return "timestamp is not a number";
  }
  if (ageSeconds < -Constants.Verification.FUTURE_TOLERANCE_S) {
    return String.format("picture time is %.3f s in the future", -ageSeconds);
  }
  if (ageSeconds > Constants.Vision.MAX_MEASUREMENT_AGE_S) {
    return String.format(
        "picture is %.3f s old (limit %.1f s)",
        ageSeconds,
        Constants.Vision.MAX_MEASUREMENT_AGE_S);
  }
  return null;
}

And how it keeps a separate verdict for each of the camera’s two streams, in VisionSubsystem.java — do not paste

mt1TimestampProblem[i] =
    updatedTimestampProblem(mt1TimestampProblem[i], connected, now, frames[i].mt1());
mt2TimestampProblem[i] =
    updatedTimestampProblem(mt2TimestampProblem[i], connected, now, frames[i].mt2());

The first method returns a sentence, or null for “fine”. That sentence ends up in the vision.timestamp alert and on the Pre-Match tab, so whoever reads it knows what to fix. The second excerpt is the follow-up fix that keeps MegaTag1 and MegaTag2 apart, because they arrive separately. One shared verdict allowed a good MegaTag2 packet to hide a bad MegaTag1 one.
