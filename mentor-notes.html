Preparing a programming session

A small, working starting point gives beginners room to learn one thing at a time.

Prepare the student starting point

The website archive contains teaching pages, not the team's baseline Java project. Supply the robot training repository and check it against these instructions before using Activities 0–9. The Java introduction and simulated-light activity use a normal WPILib 2026 Command Robot project.

  • Provide the approved 2026 installer, repository URL, exact starter tag/commit, controller map, and a known working AdvantageScope layout. Keep 2027 alpha/bench work separate.
  • On a student machine, build and launch the sandbox and training project once before class. Verify vendor libraries and simulation support. Use a local project folder outside cloud sync.
  • Check the simulator joystick port and a keyboard mapping for students without a gamepad. Demonstrate mode selection, enable, disable, and how to stop simulation.
  • Check the complete live log paths, including Template/Winner, Template/ActiveRequests, Template/OutputPercent, Template/TimeoutFired, and Drivetrain/Pose. Match the code and pages if they differ.
  • Use a training repository with one cumulative branch per student/pair. Keep the learning PR open across activities. Decide what belongs in the training main branch before merging duplicate exercise changes.

Resolve these starter-dependent details

The older lessons described different implementations. The supplied final 2026 repository confirms commented-out requirements in request commands and declaration-order intake arbitration; it is historical code, not the missing teaching baseline. These revisions make the distinction explicit; they do not claim the absent robot source has been repaired.

  1. Requests and requirements: run A → A+B → A. Two commands requiring the same subsystem cannot run together. A retained-request manager needs an explicit ownership design distinct from ordinary competing commands. Keep requirements for commands that control hardware; do not remove them as a shortcut. Document the actual path before teaching simultaneous requests.
  2. Priority: inspect whether arbitration compares numeric priority or walks declaration order, and whether validateOrdering() exists. Activity 4 now asks students to observe the implemented contract rather than promising one specific crash.
  3. Bindings: identify actual slow-mode and aiming buttons; the original pages disagreed. Check that new Y, POV-up, and right-stick bindings do not replace existing actions.
  4. Later activities: identify the field-layout field and load it once; provide the existing aim helper and named-command registration location. Supply a working DriveOffLine auto and a way to toggle the simulated goal sensor.

A suggested first four meetings

MeetingPracticeIndividual checkpoint
1Hello Robot, one changed message, one repaired syntax errorPredict two printed lines and find the first useful error
2Variables, threshold checks, short loops, methodsExplain below/equal/above a boundary and where a method goes
3Objects and the simulated-light commandExplain the field, command start, timeout, and cleanup
4Activities 0–2: Git, simulation, dashboard, counterFind the shared commit and explain the graph

Use 60–90 minutes as a planning estimate, not a deadline. Swap driver/navigator roles every 10–15 minutes. Ask each student to explain or change something; do not let the more experienced partner do all the typing.

Use the reference when it helps

Read logging alongside Activity 1, requests alongside Activities 3–4, and field geometry alongside Activities 6–7. Vision tuning, PID, and SystemCore migration are later topics. Ask students to predict, run, explain, and change one thing. Normalize asking for help after a short focused attempt.

Examples from our 2026 robot provides four short readings. Keep the full historical architecture out of the first lessons.
