Make the first result easy to reach

Assume every student is new to programming. Lessons 1–7 use a plain WPILib 2026 Command Robot sandbox; they do not need the full competition repository, vendor libraries, a gamepad, or a robot. Lesson 8 adds a pretend light and one command in the same sandbox.

The website ZIP contains teaching pages, not a ready-to-run Java project. Before class, follow the lessons on a student machine and record the exact approved stable-2026 version. The October 10 review compiled and ran 29 startup examples and all 52 workbook answer checks against actual WPILib 2026.2.2 libraries, using JDK 25 with Java 17 compatibility. The Lesson 8 classes also compile. Full simulation, the VS Code workflow and hardware behavior still need a classroom walkthrough.

Before the first session

  1. Provide the approved WPILib 2026 installer and help with installation permissions. Keep the 2027 alpha tools and SystemCore bench separate.
  2. Create the lesson sandbox outside cloud sync, build it, and launch its simulation once. Verify that the lesson’s robotInit message appears in the VS Code Terminal while disabled.
  3. Check that students can find Explorer, the editor, the command palette, and Terminal. Demonstrate saving and stopping a simulation.
  4. Walk through all eight lessons before using them in class. For Lesson 8, confirm Autonomous starts the light, the timeout turns it off, and early Disable also turns it off.
  5. Have a known working copy for comparison. Help students identify a small difference before replacing whole files.

Plan for repetition and breaks

Use 45–75-minute meetings as a planning range, not a deadline. Installation may need its own session. If a student can copy code but cannot predict a change yet, repeat that idea before introducing the next one.

SessionFocusIndividual check before moving on
1Tools and first message (Lessons 1–2); split if setup takes time.Find the file, change the message, save, run, and find the output.
2Variables (Lesson 3), plus a short recap of running code.Predict a value before and after an assignment.
3Decisions (Lesson 4).Test below, equal to, and above a boundary; explain which branch ran.
4Methods (Lesson 5).Show the definition and a call; explain an argument and a returned result.
5Bounded loops (Lesson 6).Trace three passes and the final condition check on paper.
6–7Objects (Lesson 7); repeat with different starting counts.Explain why two objects can hold different counts.
8 or laterOne simulated command (Lesson 8).Explain what starts the action and what cleans it up.

These are suggestions, not eight mandatory deadlines. A confident student can combine sessions; another may need more time. Give everyone their own turn to predict, type, and explain. Two beginners can pair successfully: one reads and predicts while the other types, then they swap after 10–15 minutes.

Use a short teaching routine

  1. Recall: ask the student to run their last working example and explain one line.
  2. Model: read the next small block aloud. Point at the exact place it goes.
  3. Predict: have the student write the output they expect.
  4. Try: let the student run it and compare. A different result is evidence to investigate.
  5. Change: ask for one new value or message without copying a full solution.
  6. Close: record the lesson, last working result, and next question in learning-notes.txt.

After about five focused minutes stuck, help narrow the problem. Ask “What did you expect?” and “What was the last change?” before taking the keyboard. Read the first useful build error together. Avoid introducing extra libraries to solve a basic syntax mistake.

Use last year’s code as a reading exercise

The four guided readings explain new terms, trace a result, and provide hints and answers. Readings 1–2 follow objects; 3–4 follow commands. Do one at a time. Students do not need to infer a complete design from an excerpt or copy it into their sandbox.

When students are ready for the team project

The older team-project activities and architecture reference are later material. The teaching baseline source is absent from this website archive; the final 2026 competition code is a separate historical reference. Supply a tested training repository before using those activities.

  • Provide the repository URL, starter commit/tag, controller map, simulator joystick port, keyboard alternative, and AdvantageScope layout.
  • Verify the actual log paths, including Template/Winner, Template/ActiveRequests, Template/OutputPercent, Template/TimeoutFired, and Drivetrain/Pose; align the pages with the starter where they differ.
  • Check A → A+B → A behavior. Two ordinary commands requiring the same subsystem cannot run together. A retained-request manager needs an explicit ownership design; removing requirements is not a shortcut.
  • Inspect whether priority uses a numeric comparison or declaration order. Match Activity 4 to the implementation.
  • Confirm actual aiming/slow-mode buttons, field-layout loading, aim helper, named-command registration, DriveOffLine auto, and the simulated goal-sensor control before assigning their later activities.
  • Use the Git walkthrough with one cumulative branch per learner/pair and small commits. Decide how practice work should be reviewed before merging anything.

Vision tuning, PID, retained-request arbitration, field geometry, and SystemCore migration can wait until students have a reason to use them.
