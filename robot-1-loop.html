1. A program that never ends

Your lesson programs printed a few lines and then finished. A robot program is different. The standard TimedRobot template requests one pass every 20 milliseconds (0.02 s), about 50 passes per second. This is a configurable target period; slow code can miss it.

Each pass is short. It reads the controller and sensors, decides what to do right now, sends new requests to the motors, and finishes. The next pass does it all again with fresh readings.

2. Watch the loop run

A reminder from Lesson 7B: 7 % 3 is 1: divide 7 by 3 and keep the remainder. 6 % 3 is 0. With two integers, 7 / 3 is 2: the fractional part is discarded. Thus loopCount % 50 == 0 selects passes 50, 100 and 150, while loopCount / 50 counts whole groups of 50.

We will count passes and print once every 50, about once a second at the default loop period. This counter estimates elapsed time; use a clock or WPILib Timer when actual time matters.

Where this goes: open src/main/java/frc/robot/Robot.java in sim-starter with Ctrl+P. Add the field beside the other fields, outside all methods. Add the counter lines immediately after the existing scheduler call in robotPeriodic. Keep every other line of that method; the simulation also updates its model and browser display there.

3. Modes: what runs when

WPILib calls different methods depending on the robot’s mode. The robot starts disabled. In a match it then runs autonomous, is disabled briefly, then runs teleop (driver control).

4. Never wait inside the loop

Here is the most important rule of robot code. Suppose you want to print a message when the driver presses A. Someone new to robot code might write a loop that waits:

Don’t do this

Reading example — do not paste

// DON'T DO THIS: the whole robot freezes until the button is pressed
while (!controller.getAButton()) {
    // waiting...
}
System.out.println("A pressed");

While this while loop spins, the pass never finishes. The main scheduler stops responding. A motor controller might continue its last request until a safety mechanism stops it; the result depends on the controller and configuration. Do not rely on that to make blocking code safe. WPILib notices a pass that takes too long and prints a warning that mentions a loop overrun.

Instead, ask the question once per pass and react when the answer changes:

Reading example — the robot-code way

// Do this instead: ask once per loop, and react when the answer changes
if (controller.getAButtonPressed()) {
    System.out.println("A pressed");
}

This is why the light command in Lesson 8, coming up soon, needs no loop or pause. The scheduler checks its timeout on every pass and calls end() when the time is up. The practice workbook’s PracticeBlinker uses the same idea: count passes instead of waiting.

public void robotPeriodic() {
  // Runs every subsystem's periodic(), checks every button, runs every active command.
  // Nothing in command-based code happens without this line.
  CommandScheduler.getInstance().run();
}

And the start of the vision subsystem’s periodic(), which that line runs every 20 ms — do not paste

public void periodic() {
  double now = Utils.getCurrentTimeSeconds();
  SwerveDriveState state = drivetrain.getState();

  // 1) Heartbeats, pipelines, and our heading -> every camera.
  double headingDeg = state.Pose.getRotation().getDegrees();
  double turnRateDegPerSec = Math.toDegrees(state.Velocity.omega);
  for (int i = 0; i < cameras.length; i++) {
    LimelightNT camera = cameras[i];
    camera.updateHeartbeat(now);
    boolean connected = camera.isConnected(now, Constants.Vision.HEARTBEAT_TIMEOUT_S);
    // ... more checks for this camera ...
  }
  // ... use the pictures ...
}

The first excerpt is the heartbeat. Every 20 ms, WPILib calls robotPeriodic(), and the scheduler runs every subsystem’s periodic(). The second excerpt is one of those. Each pass it reads the robot clock (now), asks the drivetrain for its latest state, and loops over every camera. Nothing in it waits: it checks, decides, and returns in time for the next tick.

One 2027 difference: the practice bot has no robotInit(). Its start-up code goes in the Robot() constructor, which runs once, before the loop starts.
