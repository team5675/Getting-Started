1. Counting steps with your eyes closed

Close your eyes, take ten steps forward, turn right, and take five more. You can guess where you are by adding up your steps and turns. That is dead reckoning. Robots do the same thing, called odometry.

Each tiny move comes from sensors the robot already has:

SensorWhat it tells odometryWhat fools it
Drive motor encodersHow far each wheel rolledWheels slipping or skidding on carpet; a robot that is lifted and carried
CANcodersWhich way each wheel pointed while it rolledWrong module offsets, a loose magnet, mechanical play, stale data or a sensor fault
Pigeon 2 gyroWhich way the whole robot faces, measured directlyA small slow drift over time; a wrong starting heading

Notice what is missing: nothing here measures where the robot is on the field. Odometry only knows where the robot is compared with where it started.

3. Simulate a robot whose wheels slip

We will keep two poses. truth is where a pretend robot really is. odometry is where its program thinks it is. The real robot drives 50 steps of 10 cm. Its wheels slip a little, so the program counts 10.3 cm per step.

Where this goes: replace only the practice() method. Add the helper method printComparison below it, inside the Robot class. If printModules from the previous page is still there, you may keep it or delete it.

Code to use: practice

private void practice() {
    Pose2d truth = new Pose2d(1.0, 1.0, Rotation2d.kZero);    // where the robot really is
    Pose2d odometry = new Pose2d(1.0, 1.0, Rotation2d.kZero); // where the robot thinks it is

    Transform2d trueStep = new Transform2d(0.10, 0.0, Rotation2d.kZero);     // what really happened
    Transform2d countedStep = new Transform2d(0.103, 0.0, Rotation2d.kZero); // wheels slipped 3%

    for (int i = 0; i < 50; i++) {
        truth = truth.plus(trueStep);
        odometry = odometry.plus(countedStep);
    }

    printComparison(truth, odometry);
}

Code to use: new helper method, below practice

private void printComparison(Pose2d truth, Pose2d odometry) {
    double error = odometry.getTranslation().getDistance(truth.getTranslation());
    System.out.println("Real robot:    x=" + String.format("%.2f", truth.getX())
        + " y=" + String.format("%.2f", truth.getY()));
    System.out.println("Odometry says: x=" + String.format("%.2f", odometry.getX())
        + " y=" + String.format("%.2f", odometry.getY()));
    System.out.println("Error: " + String.format("%.2f", error) + " m");
}
PieceWhat it does here
Rotation2d.kZeroA ready-made angle of 0°: facing +X, toward the red wall.
new Transform2d(0.10, 0.0, Rotation2d.kZero)A move measured from the robot’s own point of view: 0.10 m forward, nothing sideways, no turn.
truth.plus(trueStep)Apply that move starting from the pose. “Forward” means the way the pose faces, so the heading matters.
truth = truth.plus(...)A Pose2d cannot be changed after it is made. plus returns a new pose, so we store it back in the same variable. (Your Counter worked differently: its increment() changed the object itself.)
getDistance(...)The straight-line distance between where odometry thinks the robot is and where it really is.

Run the new version: save with Ctrl+S, stop the previous simulation, then type .\robot. Watch the VS Code Terminal. These startup examples run while the simulator is disabled. No robot, controller or camera is needed.

Expected output — read this; do not paste it into Java

Real robot:    x=6.00 y=1.00
Odometry says: x=6.15 y=1.00
Error: 0.15 m

Each step was only 3 mm wrong, but 50 steps make 15 cm. The error did not cancel out; it piled up.

4. A small heading mistake

Now make the wheels perfect, but start the program with a heading that is 2° wrong. That can happen if the robot was set down slightly crooked and someone told it “you face exactly 0°.”

Where this goes: replace practice again. Keep printComparison.

Code to use

private void practice() {
    Pose2d truth = new Pose2d(1.0, 1.0, Rotation2d.kZero);
    Pose2d odometry = new Pose2d(1.0, 1.0, Rotation2d.fromDegrees(2)); // heading 2 degrees wrong

    Transform2d step = new Transform2d(0.10, 0.0, Rotation2d.kZero); // wheels measure perfectly now

    for (int i = 0; i < 50; i++) {
        truth = truth.plus(step);
        odometry = odometry.plus(step);
    }

    printComparison(truth, odometry);
}

Expected output — read this; do not paste it into Java

Real robot:    x=6.00 y=1.00
Odometry says: x=6.00 y=1.17
Error: 0.17 m

A 2° error sounds tiny, but over 5 m it moves the robot’s idea of its position 17 cm sideways: 5 m × sin(2°) ≈ 0.17 m. Drive farther and the error grows with it.

5. Why odometry alone is not enough

During a match the robot drives, turns, gets bumped and skids. Every one of those moments adds a little error, and nothing in odometry ever removes it. After a couple of minutes, odometry alone can be tens of centimeters off, sometimes more.

Heading is usually more stable than wheel-based position. The gyro measures rotation, so wheel slip does not directly corrupt it. It still needs an initial field alignment and fresh, healthy data; drift, a reset or a fault can make its heading wrong. That is why, on the practice bot, cameras are allowed to correct the robot’s x and y while it drives, but not its heading.

The carried robotIf you lift the robot and carry it, the wheels don’t turn, so odometry thinks the robot never moved. The gyro still notices turns. This is why the Pre-Match tab never shows the start position as green unless a camera can see an AprilTag: the map may be showing where the robot used to be.

CTRE’s swerve library runs odometry in its own fast loop, about 250 times a second on the practice bot (Drive/OdometryHz). The practice-bot code also keeps a second, odometry-only pose that cameras never correct, logged as Drive/OdometryOnlyPose. Drive around and compare it with Drive/Pose in AdvantageScope: the two estimates can separate. Neither trace is ground truth: compare them with an independent physical reference. A bad camera or mount can move the corrected pose the wrong way, and this second tracker also runs at a different update rate.

Reading example from src/main/java/frc/robot/subsystems/drivetrain/CommandSwerveDrivetrain.java, inside periodic() — do not paste

SwerveDriveState state = getState();
Rotation2d gyro = rawHeading(state);
Pose2d odometryOnlyPose = odometryOnly.update(gyro, state.ModulePositions);

Logger.recordOutput("Drive/Pose", state.Pose);
Logger.recordOutput("Drive/OdometryOnlyPose", odometryOnlyPose);

odometryOnly.update(gyro, modulePositions) is the add-up-tiny-moves idea from this page in one call, fed with the gyro heading and the four wheels’ distances and angles. Its result is logged next to the camera-corrected Drive/Pose, so the two can be compared on the same graph.
