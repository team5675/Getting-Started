CH 1The road ahead

No computer needed for this page — just read.

A program is a list of exact instructions a computer follows, in order, one at a time. Nothing more, nothing less. Computers are incredibly fast, but they are also incredibly literal: they will do exactly what you tell them, even when that's not what you meant. Learning to program is really learning to think in a way that doesn't leave anything out or assume the computer will "figure out what you meant."

We write our instructions in a language called Java. Java is what most FRC teams use, and it's what WPILib — the official FRC programming toolkit — is built around. A competition robot's program is, underneath everything, a loop that runs about 50 times every second, constantly asking: what are my sensors seeing right now, and what should the motors do about it? That's genuinely most of what a robot program is. Everything in this guide builds toward being able to read and write that loop.

CH 2Installing your toolbox

We use exactly one thing: the WPILib installer. It gives you a special, separate copy of the VS Code editor, bundled together with Java itself, the build tool (Gradle), every FRC library, and the dashboards (AdvantageScope, Elastic, and others) — all matched to work together, so everyone on the team has an identical setup.

  1. Team 5675 is programming on WPILib 2026, targeting the classic roboRIO control system — the same one that ran the 2026 competition robot. (A couple of upperclassmen are separately bench-testing a future controller called SystemCore for the 2027 season, on its own alpha install — that's a different project, not this guide, and not something you need yet.) Go to docs.wpilib.org → "Zero to Robot" → Step 2, and download the newest stable release (currently WPILib 2026, version 2026.2.1) for your operating system.
  2. Run it. When it asks about VS Code, choose "Download for this computer only" — WPILib can't legally bundle VS Code directly, so the installer fetches its own copy for you. Just let it.
  3. Pick the full install (Java tools + all WPILib tools). It downloads several gigabytes — this is a good moment for a snack.
  4. When it finishes, launch "WPILib VS Code 2026" specifically — not your computer's regular VS Code, and not a plain copy downloaded from Microsoft. Every season gets its own separate copy, so a 2025 or 2027-alpha install on the same laptop won't ever conflict with this one.

Check it worked: in WPILib VS Code, press Ctrl+Shift+P (Cmd+Shift+P on a Mac) and type WPILib. A long list of WPILib-specific commands should appear. If you see that list, you're set up correctly.

Common mistake Don't install a second, ordinary copy of VS Code and add Java extensions to it yourself to "make it work" — you'll spend build season fighting version mismatches nobody else on the team has. One install: WPILib VS Code. That's it.
Companion reading Installing WPILib and VS Code (Code with Kate) walks through this same process with screenshots, if you want a second explanation alongside this one.

CH 3Hello, robot!

Goal for this chapter: write one line of your own code, run it on a simulated robot, and see proof that it ran. This is the entire edit → build → run → observe loop you'll use for the rest of the season — we're just doing it for the first time.

  1. In WPILib VS Code: Ctrl+Shift+P → WPILib: Create a new project → Template → Java → Command Robot → team number 5675 → name it something like learning-sandbox, saved somewhere that is not the team's real repository. This is your personal scratch space for this whole guide.
  2. Open Robot.java and find the method robotInit(). This runs exactly once, the instant your program starts.
  3. Add one line inside it: 
    System.out.println("Hello, robot!");
  4. Ctrl+Shift+P → WPILib: Simulate Robot Code. A simulation window opens, along with a console/log panel.
  5. Find Hello, robot! printed in that console the instant it starts.

What each piece means: public class Robot is a class — a container for code (Chapter 8 goes deeper). robotInit() is a method — a named block of instructions (Chapter 7). System.out.println(...) is a built-in Java command that prints text; the quotes mark "Hello, robot!" as literal text, called a String.

Try it yourself Change the message to include your own name. Then add a second println line right below the first. Re-simulate: both lines should appear, top to bottom, in the exact order you wrote them — programs run one line at a time, in order, no skipping around unless you tell them to (that's Chapters 5 and 6).
Why this matters for the robot This is the whole game: edit code, build it, run it (simulated or real), observe the result. Exercise 2 of the team's real ladder is this exact loop, on the real codebase — you're already trained on it.
If you have a Romi Team 5675 also has a Romi — a small two-wheeled practice robot that runs real WPILib command-based Java code on real hardware, with none of the swerve/Kraken complexity. Everything in this guide works fine in simulation with no Romi needed, but if one's free, ask a mentor for the Romi web setup steps and deploy this exact "Hello, robot!" program to real hardware instead of just the simulator.

CH 4Storing information: variables

A variable is a labeled box that holds one piece of information, so your code can refer to it by name instead of retyping the value everywhere. Four types you'll use constantly:

TypeHoldsExample
inta whole numberint loopCount = 0;
doublea decimal number — almost everything physical: speed, distance, voltage, angledouble batteryVoltage = 12.6;
booleantrue or false, nothing elseboolean isEnabled = true;
StringtextString teamNumber = "5675";
Try it yourself In robotInit(), declare an int for your age and a double for your height in inches. Print a sentence that includes both, joined with +: 
System.out.println("I am " + age + " years old and " + heightInches + " inches tall.");
Common mistake Forgetting the semicolon at the end of a line — Java will refuse to build until you fix it, and the error message names the exact line. Also: trying to put a decimal number into an int variable won't compile. That's not Java being difficult for no reason — it's catching a real mistake before your robot ever moves.
Why this matters for the robot Every number in the real Constants.java — motor CAN IDs, wheel size, PID numbers — is just a variable with a clear name, so nobody has to remember what the raw number 0.1016 means (it's a wheel radius, in meters).

CH 5Making decisions: if / else

A boolean expression — built with ==, !=, <, >, <=, >= — is a yes/no question. if runs a block of code only when the answer is yes; else covers the "no" case.

double batteryVoltage = 11.2;
if (batteryVoltage < 11.5) {
    System.out.println("Warning: battery low!");
} else {
    System.out.println("Battery OK.");
}
Try it yourself Declare double distanceMeters. If it's less than 1.0, print "too close!"; otherwise print "clear". Change the value and re-simulate to see both branches run.
Why this matters for the robot The pre-match health check you'll meet later (SystemHealthCheck) is a carefully-named pile of exactly these if-statements: "if battery voltage is below X, raise an alert."

CH 6Doing things over and over: loops

A for loop repeats a known number of times. A while loop repeats until a condition becomes false.

for (int i = 1; i <= 10; i++) {
    System.out.println(i);
}

Read it as: start with i at 1; keep going while i <= 10 is true; after each pass, increase i by one.

Try it yourself Use a for loop to print the 5-times table: 5, 10, 15, … up to 50.
Common mistake Forgetting to update the loop variable (leaving out i++) creates an infinite loop — the condition never becomes false. The simulator window will just hang. If that happens, stop the simulation and check your loop's update step.
Why this matters for the robot The robot's entire running life is a loop. robotPeriodic() and every subsystem's periodic() run automatically about 50 times a second while the robot is on — you never write that outer loop yourself, WPILib runs it for you, but everything inside behaves exactly like the loop body you just wrote.

CH 7Organizing code: methods

A method is a named, reusable recipe. You give it ingredients (parameters), and it can hand back a result (a return value).

double average(double a, double b) {
    return (a + b) / 2.0;
}

// used inside robotInit():
System.out.println(average(4.0, 10.0));   // prints 7.0
Try it yourself Write a method that takes two doubles and returns their average (as above), then call it with two different pairs of numbers and print both results.
Why this matters for the robot execute(), isFinished(), and periodic() are just methods with specific names WPILib expects and calls for you at the right moment. You're not learning new magic in the real codebase later — just new method names with a job already defined for them.

CH 8Blueprints: classes and objects

A class is a blueprint. An object is one specific thing built from that blueprint. Robot, RobotContainer, every Subsystem and Command you'll ever see — all classes.

class Dog {
    String name;

    Dog(String name) {       // constructor — runs when you build one
        this.name = name;
    }

    void bark() {
        System.out.println(name + " says woof!");
    }
}

// used inside robotInit():
Dog rex = new Dog("Rex");
Dog belle = new Dog("Belle");
rex.bark();     // "Rex says woof!"
belle.bark();   // "Belle says woof!"
Try it yourself Add a second field to Dog — int age — and a new method printInfo() that prints the name and age together. Update the constructor to accept and store the age too.
Why this matters for the robot A Subsystem is just a class representing one physical part of the robot (the drivetrain, an arm) — fields for its motors and sensors, methods like drive() or stop(). A Command is just a class representing one action. You already know how to read both.

CH 9From Java to robots: Subsystems and Commands

Here's the one big idea behind every FRC robot's code: Subsystems are nouns — what the robot has or is. Commands are verbs — what the robot does. A Command uses one or more Subsystems to do its job; a Subsystem never decides on its own to do something — it waits to be told.

A made-up (not the team's real code) example — a light that can blink:

class LightSubsystem extends SubsystemBase {
    void turnOn()  { /* tell the real hardware to turn on */ }
    void turnOff() { /* tell the real hardware to turn off */ }
}

class BlinkCommand extends Command {
    LightSubsystem light;

    BlinkCommand(LightSubsystem light) {
        this.light = light;
        addRequirements(light);   // "I need exclusive use of this Subsystem"
    }

    @Override public void execute() {
        // toggle on/off — runs every ~20ms while this command is scheduled
    }
}

RobotContainer's job is to build exactly one instance of each Subsystem, and wire up which Commands run when which buttons are pressed. That's exactly what you'll be reading (and eventually writing) in the real RobotContainer.java.

One thing deliberately not covered yet: once a Subsystem exists, you'll usually want to see what it's doing on a live dashboard — that's the job of a logging framework called AdvantageKit. You don't need it to understand what a Subsystem or Command is, so it waits until this pattern is second nature — you'll meet it in the teaching guide for the real codebase.

Why this matters for the robot This is exactly the shape of TemplateSubsystem and TemplateRequest you'll meet in Exercises 2 through 4 of the real ladder — same idea, with a few extra safety patterns (request arbitration) the team learned the hard way in 2026.
