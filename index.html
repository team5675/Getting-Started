From "I've never coded" to your first robot program.

Learn robot programming one small change at a time. In each chapter, you'll try something, run the code, and look at what happens. Start with a working project and gradually make more of it your own. No programming experience is needed.

Your first meeting

Start with chapters 1–3. Your goal is to run a program, change its message, and explain where the new message came from. You do not need a robot or a gamepad.

  1. Ask a mentor to help finish the tool setup.
  2. Follow Hello, robot! and make one change of your own.
  3. Show a partner the result. Take turns at the keyboard every 10–15 minutes.

If a result differs from your prediction, use that difference to decide what to check next. Ask for help when you need it. There is no race to finish.

CH 1The road ahead

No computer needed for this page — just read.

A program is a list of exact instructions a computer follows, in order, one at a time. For now, we will trace one short block of instructions at a time. Computers are incredibly fast, but they are also incredibly literal: they will do exactly what you tell them, even when that's not what you meant. Learning to program is really learning to think in a way that doesn't leave anything out or assume the computer will "figure out what you meant."

We write our instructions in a language called Java. Java is what most FRC teams use, and it's what WPILib — the official FRC programming toolkit — is built around. A competition robot's program is, underneath everything, a loop that runs about 50 times every second, constantly asking: what are my sensors seeing right now, and what should the motors do about it? That repeated check is central to robot programming. Everything in this guide builds toward being able to read and write that loop.

CH 3Hello, robot!

Goal for this chapter: write one line of your own code, run it on a simulated robot, and see proof that it ran. This is the entire edit → build → run → observe loop you'll use for the rest of the season — we're just doing it for the first time.

  1. In WPILib VS Code: Ctrl+Shift+P → WPILib: Create a new project → Template → Java → Command Robot → team number 5675 → name it something like learning-sandbox. On Windows, use a local folder such as C:\dev as the base folder. Keep this practice project outside OneDrive and separate from the team's robot repository.
  2. In the Explorer panel, open src/main/java/frc/robot/Robot.java. Find public Robot(), the constructor, and the closing brace for that constructor. Keep the existing constructor and all other methods. The 2026 template does not include a robotInit() override, so add this complete method immediately after the constructor's closing brace, still inside the Robot class:
// Add this method inside the Robot class, outside its other methods.
@Override
public void robotInit() {
    // WPILib calls this once when the program starts.
    System.out.println("Hello, robot!");
}

If your starter already has robotInit(), add only the print line inside that existing method. Java cannot have two methods with this same name and parameters.

  1. Ctrl+Shift+P → WPILib: Simulate Robot Code. A simulation window opens when the build succeeds. Select the Simulation GUI if prompted. Look in the VS Code Terminal panel for program output.
  2. Find Hello, robot! printed in that console when the program starts. This message appears while disabled; you do not need to enable the simulator for this chapter.

What each piece means: public class Robot is a class — a container for code (Chapter 8 goes deeper). robotInit() is a method — a named block of instructions (Chapter 7). System.out.println(...) is a Java method call that prints text; the quotes mark "Hello, robot!" as literal text, called a String.

Try it yourself Change the message to include your own name. Then add a second println line right below the first. Re-simulate: both lines should appear, top to bottom, in the exact order you wrote them — programs run one line at a time, in order, no skipping around unless you tell them to (that's Chapters 5 and 6).
Why this matters for the robot This edit → build → run → observe cycle is how you will investigate robot behavior. Activity 2 in Robot Programming Practice uses the same cycle to graph a value.
If you have a Romi Team 5675 also has a Romi, a small two-wheeled practice robot. Its Java program runs on your laptop and communicates with the Romi through WPILib simulation. Ask a mentor to help open a configured Romi project and use Simulate Robot Code. Do not deploy this generic project directly to the Romi. WPILib's Romi instructions explain that setup. You can finish this guide without a Romi.
If you're stuck: finding and fixing the first error
  1. Save Robot.java with Ctrl+S. Run WPILib: Build Robot Code.
  2. If the build fails, read the first relevant error in the Terminal panel. It often names a file and line. Check that line and the one above it for a missing quote, semicolon, or brace.
  3. If the build succeeds but the message is absent, stop the previous simulation using the terminal's stop/trash control (or Ctrl+C in that terminal), then simulate again.
  4. If you're still stuck after about five focused minutes, show a mentor the first error, what you expected, and the last change you made.

Practice recovering: remove the semicolon from the print line, build, and find the error. Put the semicolon back and build again. Errors are information you can use.

CH 4Storing information: variables

A variable is a labeled box that holds one piece of information, so your code can refer to it by name instead of retyping the value everywhere. Four types you'll use constantly:

TypeHoldsExample
inta whole numberint loopCount = 0;
doublea decimal number — almost everything physical: speed, distance, voltage, angledouble batteryVoltage = 12.6;
booleantrue or false, nothing elseboolean isEnabled = true;
StringtextString teamNumber = "5675";
Try it yourself In robotInit(), declare an int for your age and a double for your height in inches. Print a sentence that includes both, joined with +: 
System.out.println("I am " + age + " years old and " + heightInches + " inches tall.");
Common mistake Forgetting the semicolon at the end of a line — Java will refuse to build until you fix it, and the error message names the exact line. Also: trying to put a decimal number into an int variable won't compile. That's not Java being difficult for no reason — it's catching a real mistake before your robot ever moves.
Why this matters for the robot Every number in the real Constants.java — motor CAN IDs, wheel size, PID numbers — is just a variable with a clear name, so nobody has to remember what the raw number 0.1016 means. A name such as wheelDiameterMeters tells you both the measurement and its units.
Companion reading Java Fundamentals and Operators (FRCSoftware.org) cover this same ground with their own exercises, on the same 2026-stable toolchain we use.

CH 5Making decisions: if / else

A boolean expression — built with ==, !=, <, >, <=, >= — is a yes/no question. if runs a block of code only when the answer is yes; else covers the "no" case.

Put this example inside robotInit(). If you already declared a variable called batteryVoltage there, replace its declaration rather than adding a second one.

double batteryVoltage = 11.2;
if (batteryVoltage < 11.5) {
    System.out.println("Warning: battery low!");
} else {
    System.out.println("Battery OK.");
}
Try it yourself Declare double distanceMeters. If it's less than 1.0, print "too close!"; otherwise print "clear". Change the value and re-simulate with 0.9, 1.0, and 1.1. Predict each result first. Explain why exactly 1.0 prints clear.
Why this matters for the robot The pre-match health check you'll meet later (SystemHealthCheck) is a carefully-named pile of exactly these if-statements: "if battery voltage is below X, raise an alert."
Companion reading Conditionals (FRCSoftware.org) — more practice problems on if/else, same toolchain.

CH 6Doing things over and over: loops

A for loop repeats a known number of times. A while loop repeats until a condition becomes false.

Add this short loop inside robotInit(), after your earlier print statements.

for (int i = 1; i <= 10; i++) {
    System.out.println(i);
}

Read it as: start with i at 1; keep going while i <= 10 is true; after each pass, increase i by one.

Try it yourself Use a for loop to print the 5-times table: 5, 10, 15, … up to 50.
Common mistake Forgetting to update the loop variable (leaving out i++) creates an infinite loop — the condition never becomes false. The simulator window will just hang. If that happens, stop the simulation and check your loop's update step.
Why this matters for the robot WPILib calls robotPeriodic() repeatedly; the command scheduler calls registered subsystems' periodic() methods. With the standard setup this is about 50 calls per second. Each call must finish so other work can run. Do not put a loop that waits for a sensor inside one of these methods. Check the sensor once per call and return; later activities use command completion and timeouts.
Companion reading Loops (FRCSoftware.org) — more practice problems on for/while, same toolchain.

CH 7Organizing code: methods

A method is a named, reusable recipe. You give it ingredients (parameters), and it can hand back a result (a return value).

In Robot.java, add this method inside the class but outside robotInit(). A method declaration cannot go inside another method.

private double average(double a, double b) {
    return (a + b) / 2.0;
}

Then add this call inside robotInit():

System.out.println(average(4.0, 10.0));   // prints 7.0
Try it yourself Write a method that takes two doubles and returns their average (as above), then call it with two different pairs of numbers and print both results.
Why this matters for the robot execute(), isFinished(), and periodic() are methods the robot framework calls at particular times. @Override tells Java that your class supplies its version of an inherited method. Later, you'll trace when each one runs.
Companion reading Methods and Mutable State (FRCSoftware.org) — more practice problems on methods, same toolchain.

CH 8Blueprints: classes and objects

A class is a blueprint. An object is one specific thing built from that blueprint. Robot, RobotContainer, every Subsystem and Command you'll ever see — all classes.

Create Dog.java beside Robot.java in src/main/java/frc/robot/. Put this complete class in the new file. package identifies its folder group; this.name means this object's field, while name on the right is the constructor's parameter.

package frc.robot;

public class Dog {
    String name;

    Dog(String name) {       // constructor — runs when you build one
        this.name = name;
    }

    void bark() {
        System.out.println(name + " says woof!");
    }
}

Back in Robot.java, put these lines inside robotInit(). new constructs an object by calling its constructor.

Dog rex = new Dog("Rex");
Dog belle = new Dog("Belle");
rex.bark();     // "Rex says woof!"
belle.bark();   // "Belle says woof!"
Try it yourself Add a second field to Dog — int age — and a new method printInfo() that prints the name and age together. Update the constructor to accept and store the age too. Update both new Dog(...) calls to supply an age, for example new Dog("Rex", 3). Call printInfo() on both objects. Explain why they can have different ages.
Why this matters for the robot A Subsystem is a class representing one physical part of the robot (the drivetrain, an arm) — fields for its motors and sensors, methods like drive() or stop(). A Command is a class representing one action. The same class and object ideas will help you read both.
Companion reading Classes and Objects (FRCSoftware.org) — more practice problems on classes, same toolchain.

CH 9From Java to robots: Subsystems and Commands

Here's the one big idea behind every FRC robot's code: Subsystems are nouns — what the robot has or is. Commands are verbs — what the robot does. A Command uses one or more Subsystems to do its job; the subsystem owns its state and hardware access. Its methods and periodic() can maintain that state; commands request actions.

This sketch shows the class relationships. It is a reading example with empty bodies, not a complete program. Next, use the linked activity to build a working simulated light:

class LightSubsystem extends SubsystemBase {
    void turnOn()  { /* tell the real hardware to turn on */ }
    void turnOff() { /* tell the real hardware to turn off */ }
}

class BlinkCommand extends Command {
    LightSubsystem light;

    BlinkCommand(LightSubsystem light) {
        this.light = light;
        addRequirements(light);   // "I need exclusive use of this Subsystem"
    }

    @Override public void execute() {
        // toggle on/off — runs every ~20ms while this command is scheduled
    }
}

RobotContainer's job is to build exactly one instance of each Subsystem, and wire up which Commands run when which buttons are pressed. That's exactly what you'll be reading (and eventually writing) in the real RobotContainer.java.

One thing deliberately not covered yet: once a Subsystem exists, you'll usually want to see what it's doing on a live dashboard — that's the job of a logging framework called AdvantageKit. You don't need it to understand what a Subsystem or Command is, so it waits until this pattern is second nature — you'll meet it in the teaching guide for the real codebase.

Why this matters for the robot These concepts help explain TemplateSubsystem and TemplateRequest you'll meet in Activities 2–4. The team's request pattern adds another layer; first practice starting and ending a single command.
Companion reading FRCSoftware.org's Stage 1B — starting at The Concepts — is a deeper, exercise-driven walkthrough of command-based programming (including a "spot the error" bonus round), on a simpler kit robot rather than swerve. Good next stop if this chapter went by fast.
Try a complete example Your first command: a simulated light provides full files, expected output, and a two-second action. No robot, gamepad, or vendor libraries are needed. Run it before moving to the team's larger project.
