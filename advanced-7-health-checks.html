Prove it is alive

Use evidence, age and a useful explanation before turning a status light green.

All lessons · Which robot code are we reading?

Today’s small goal

Explain why a number on a dashboard might be unusable, then write a health decision using fake readings. Before starting: decisions, arrays and the timestamp lesson. Allow 35–50 minutes; no camera is needed.

1. Four questions, four different facts

A camera object in Java is a way to talk to a device. Creating that object does not prove a camera is connected. Even seeing a plausible pose such as (2 m, 3 m) does not prove it describes the robot now: the network may still hold an old value.

  1. Connected?

    Has the heartbeat changed recently?

  2. Fresh?

    How old is the measurement, using the right clock and units?

  3. Usable?

    Did it pass the pipeline, tag, motion and field checks?

  4. Accepted?

    Was a correction actually handed to the estimator?

A heartbeat says the camera is talking. It does not say it sees a tag. A seeded pose says the heading was established earlier. It does not say a camera correction was accepted recently.

2. Predict a health message

For this exercise only, a measurement may be at most 0.5 seconds old. The real robot has its own named thresholds. Read the rows from the top: the first matching problem wins.

NoAnyAnyDISCONNECTED — check power/network.
YesNegative or not finiteAnyBAD_TIME — investigate clock/units.
YesOver 0.5 sAnySTALE — investigate why measurements stopped.
Yes0 to 0.5 sNoREJECTED — read the rejection reason.
Yes0 to 0.5 sYesREADY — this exercise’s checks pass.

Double.isFinite(age) checks for an ordinary finite number. NaN means “not a number”; infinity and NaN should not become green status. ! means NOT and || means OR. Unlike a real dashboard, this exercise passes the booleans in by hand so you can test every branch.

3. Try it, then break one assumption

  1. Download and open the home Java starter. Read the TASK in lessons/CameraHealth.java.
  2. Write verdict with the rules above. Use return to finish as soon as a problem is found.
  3. In the home-java-starter Terminal, run .\run CameraHealth. Expect READY then STALE.
  4. Add check to that command. Eight checks include exactly 0.5, slightly over, future time, NaN and infinity.
  5. Explain why changing the old pose’s coordinates would not make it fresh. Discuss why you should display an explanation beside a colored light.
Hint: start with the strongest evidenceFirst handle !heartbeat. Then check invalid time before comparing its age. A comparison such as NaN > 0.5 is false; that is why merely checking the upper bound is insufficient.

4. In the real robot

The reviewed main SystemHealthCheck uses these branches inside updateCameraRow(). This is a shortened reading excerpt:

if (!vision.isCameraConnected(i)) {
    light = light.worse(Light.RED);
    parts.add(name + ": no heartbeat, check its power and Ethernet");
} else if (!vision.isOnAprilTagPipeline(i)) {
    light = light.worse(Light.YELLOW);
    parts.add(name + ": not on its AprilTag pipeline");
}

parts holds sentences for the dashboard; light.worse keeps the most serious problem seen so far. The objects and calls add detail, but the decision structure is the same one you wrote.

The current reviewed robot still has a gap: its green Vision lock describes seed state, not the age of the last accepted correction. Your fake-data exercise teaches the distinction; it does not silently add that missing feature to the robot.

5. A small mentor-led investigation

On a disabled supervised bench, record the camera heartbeat, frame age, rejection reason and accepted count. Cover the tags while leaving Ethernet connected. Predict which facts should change. A running heartbeat with no accepted corrections is a useful result, not a reason to weaken the checks. Record the actual result; the at-home Java exercise does not validate hardware.

Pause and check

A camera is connected and the robot was seeded two minutes ago, but every new frame is rejected. Explain why “connected,” “seeded,” and “recent correction” should be separate labels.
