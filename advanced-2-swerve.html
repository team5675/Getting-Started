1. Four corners, two motors each

A swerve drive has a wheel unit called a module at each corner. Each module has two motors. The steer motor turns the wheel to point in a direction. The drive motor spins the wheel to roll it. Because every wheel can point anywhere, the robot can drive in any direction while facing any direction.

A CANcoder on each module measures the wheel’s angle directly, so the robot knows where its wheels point as soon as it turns on. The gyro in the middle measures which way the whole robot faces. You will need that heading in section 6.

2. Three numbers describe a motion

To move the robot, you don’t talk to eight motors. You describe the motion of the whole robot, measured from the robot’s own point of view:

NumberMeaningUnits
forwardToward the robot’s front (negative = backward)meters per second
leftToward the robot’s left side (negative = right)meters per second
turnSpin, counterclockwise seen from above (negative = clockwise)radians per second

WPILib’s class for these three numbers is ChassisSpeeds. A radian is about 57.3°, so turning 1 radian per second is a bit less than one-sixth of a full turn each second.

Working out each wheel’s angle and speed from those three numbers is called kinematics. WPILib’s SwerveDriveKinematics does it, once it knows where the modules are.

4. Ask WPILib for the wheel angles

Where this goes: replace only the practice() method, from its private void practice() line through its matching closing brace. Then add the helper method printModules below it, still inside the Robot class: after practice’s closing brace, before the class’s final closing brace.

Code to use: practice

private void practice() {
    double half = 0.3048; // half of 24 inches, in meters
    SwerveDriveKinematics kinematics = new SwerveDriveKinematics(
        new Translation2d(half, half),     // front left
        new Translation2d(half, -half),    // front right
        new Translation2d(-half, half),    // back left
        new Translation2d(-half, -half));  // back right

    printModules("Forward 1 m/s", kinematics.toSwerveModuleStates(new ChassisSpeeds(1.0, 0.0, 0.0)));
    printModules("Left 1 m/s", kinematics.toSwerveModuleStates(new ChassisSpeeds(0.0, 1.0, 0.0)));
    printModules("Spin 1 rad/s", kinematics.toSwerveModuleStates(new ChassisSpeeds(0.0, 0.0, 1.0)));
}

Code to use: new helper method, below practice

private void printModules(String label, SwerveModuleState[] states) {
    String[] names = {"Front left ", "Front right", "Back left  ", "Back right "};
    System.out.println(label + ":");
    for (int i = 0; i < states.length; i++) {
        System.out.println("  " + names[i]
            + "  speed " + String.format("%.2f", states[i].speedMetersPerSecond) + " m/s"
            + ", angle " + String.format("%.1f", states[i].angle.getDegrees()) + " degrees");
    }
}
PieceWhat it does here
new Translation2d(half, half)Where one module sits, measured from the robot’s center: x forward, y left. The front-left module is 0.3048 m forward and 0.3048 m left.
new SwerveDriveKinematics(...)Makes a calculator that knows the four module positions. The order you list them is the order the answers come back.
new ChassisSpeeds(1.0, 0.0, 0.0)The motion you want: forward 1 m/s, left 0, turn 0.
toSwerveModuleStates(...)Returns an array of four SwerveModuleState objects, one per module.
states[i].speedMetersPerSecond, states[i].angleOne wheel’s answer: how fast to roll and which way to point. These are public fields, so we read them directly without a getter method.
String[] names and the for loopPrint the four answers with readable labels, in the same order as the module list.

5. Read the three answers

For forward and left, every wheel does the same thing. Spinning is different: each wheel points along a circle around the robot’s center. Its speed is the turn rate times its distance from the center: 1 rad/s × 0.431 m = 0.43 m/s.

Why the angles look like thatAngles here use the robot’s own frame: 0° is the robot’s front, 90° its left side, and −90° its right side. The front-left wheel at 135° points backward and to the left, which is the counterclockwise direction at that corner.

6. Field-centric: drive in the driver’s directions

A driver standing behind the blue wall thinks “push the stick away from me, the robot goes away from me,” whichever way the robot’s nose points. That is called field-centric driving. The request is on the field map, so the code must convert it to the robot’s own frame using the robot’s heading.

Where this goes: add these lines inside practice, after the three printModules lines and before practice’s closing brace.

Code to use

    Rotation2d heading = Rotation2d.fromDegrees(90); // the robot faces +Y
    ChassisSpeeds robotRelative = ChassisSpeeds.fromFieldRelativeSpeeds(1.0, 0.0, 0.0, heading);
    System.out.println("Robot-relative: forward " + String.format("%.2f", robotRelative.vxMetersPerSecond)
        + ", left " + String.format("%.2f", robotRelative.vyMetersPerSecond));
    printModules("Driver pushes away, robot faces 90", kinematics.toSwerveModuleStates(robotRelative));

This is why the heading matters to drivers, not just programmers. If the robot believes it faces 70° when it really faces 90°, “away” comes out 20° off and the robot drives diagonally. Keeping the heading right is the job of the next page and the camera topics after it.

Red allianceFor a driver behind the red wall, “away from me” is −X. The robot code tells CTRE’s swerve library which way is forward for the current alliance, once, in one place. Keep operator perspective separate from the fixed blue-origin field coordinates used for pose and field-point aiming. Path mirroring is another operation, owned by the path library. Do not add a second alliance-dependent heading flip. The exact cause of an older driving bug is not established by this lesson; verify each coordinate transform with known headings on both alliances.

7. What the team’s code adds, and what CTRE’s library does

On the practice bot, a stick movement travels through these steps about 50 times a second:

Two extra rules happen inside the library. For an ordinary optimized drive request, the library chooses a target at most 90° from the wheel’s current angle: pointing backward and rolling in reverse is the same as pointing forward and rolling forward, and it is quicker. And if one wheel would need more than its top speed, all four slow down by the same fraction, so the robot still goes the right direction. (WPILib calls this desaturating the wheel speeds; CTRE’s request does it by default.)

private final SwerveRequest.FieldCentric fieldCentric =
    new SwerveRequest.FieldCentric().withDriveRequestType(DriveRequestType.OpenLoopVoltage);

This one object is the robot’s field-centric driving. Every loop, the default drive command (Part 2, “Reading a controller”) fills in the stick speeds with withVelocityX, withVelocityY and withRotationalRate. CTRE’s library then does what you did by hand: it turns field-relative speeds into robot-relative ones using the heading, runs the kinematics to get four module speeds and angles, and slows them all equally if one is too fast.

From the team’s 2027 practice-bot code (repository 2027Practice, October 2026). It is built with the 2027 test version of WPILib, so a few names differ from your 2026 tools. Read it; don’t paste it.

2027 differencesIn the WPILib 2027 alpha on the practice bot, ChassisSpeeds is renamed ChassisVelocities, SwerveModuleState becomes SwerveModuleVelocity (its speed field is called velocity), toSwerveModuleStates becomes toSwerveModuleVelocities, and the field-to-robot conversion is a method on the request itself, toRobotRelative(heading). Here “request” means the ChassisVelocities value, not a CTRE SwerveRequest. These names describe the pinned alpha-7 project, not a promised final 2027 API. Keep your practice on WPILib 2026.
