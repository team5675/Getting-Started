1. See it

Start with two choices

A condition is a question with a true/false answer. In this invented practice rule, print “Too close” if the distance is less than 1 meter; otherwise print “Clear.” A branch is the block of instructions chosen by that answer.

double distanceMeters = 1.0;
if (distanceMeters < 1.0) {
    System.out.println("Too close");
} else {
    System.out.println("Clear");
}
PAUSE & PREDICT

What happens right at the boundary?

Try 0.9, 1.0 and 1.1 meters. Which values make distanceMeters < 1.0 true? Make your prediction, then read on.

At 1.0, the question is false, so the else branch prints Clear. The other branch does not run. Read this example and try its boundary in the interactive panel below; your downloaded Decisions.java uses the voltage example next.

Then add a third possibility

A condition evaluates to true or false. < means less than; exactly equal does not pass it. Java checks an if / else if / else chain in order and runs the first matching branch.

double volts = 11.0;
if (volts < 11.0) {
    System.out.println("LOW");
} else if (volts < 12.0) {
    System.out.println("CHECK");
} else {
    System.out.println("READY");
}

These voltage thresholds are invented for practice, not a real battery policy. At 11.0, the first condition is false and the second true, so CHECK prints. else handles everything left over. Compare numbers with ==; assign with =. Keep braces around each branch. First get one comparison working; combined conditions are a later extension.

Part B · make a change yourself

Write your own decision

After the voltage example in Decisions.java, declare boolean enabled = false. Write an if/else that prints MOVING when true and STOPPED otherwise. Run both values. Then make a table of the voltage outputs for 10.9, 11.0, 11.9 and 12.0.

A hint after you try

Enabled selects MOVING or STOPPED. The voltage table is LOW, CHECK, CHECK, READY. One boundary belongs to exactly one branch.

Save your prediction, actual output and explanation. This is practice, not a speed test.

Two if mistakes with confusing results
  • if (enabled = true) runs without any error, but one = stores true instead of comparing. MOVING prints every time. Write if (enabled).
  • if (volts < 11.0); A semicolon right after the condition ends the if. Before an else, Java reports 'else' without 'if'. With no else, there is no error at all and the block below runs every time. Remove that ;.

If you get stuck

Java’s message starts with the file and the line number. Read the words after error:, fix only the first error, save, and run again.

'else' without 'if'
A semicolon right after if (...) ended the if early, or a brace is missing before else. Remove the ; and check that each { has its }.
incompatible types: double cannot be converted to boolean
The condition uses one =, as in if (volts = 11.0). Compare with <, > or ==.
Every value prints the same word
Check the two if mistakes in the box above. Then check the order of your conditions: Java runs only the first branch whose condition is true.

In the real robot · 2027Practice

Source map and exact reviewed versions · Private team repository; excerpts remain readable here.

The pre-match checklist on the driver dashboard decides what to tell the team about each camera. It uses a chain of questions, worst problem first:

Reading example from src/main/java/frc/robot/subsystems/monitor/SystemHealthCheck.java — do not paste

if (!vision.isCameraConnected(i)) {
  light = light.worse(Light.RED);
  parts.add(name + ": no heartbeat, check its power and Ethernet");
} else if (!vision.isOnAprilTagPipeline(i)) {
  light = light.worse(Light.YELLOW);
  parts.add(name + ": not on its AprilTag pipeline");
} else if (vision.hasTimestampProblem(i)) {
  light = light.worse(Light.RED);
  parts.add(
      name + ": picture times don't match the robot clock\n(see the vision.timestamp alert)");
} else {
  int tags = vision.getVisibleTagCount(i);
  parts.add(name + " sees " + tags + (tags == 1 ? " tag" : " tags"));
}

Read it like your distance check, with more branches. ! means “not”, so the first question is “is this camera NOT connected?” Only one branch runs. The order matters: if a camera has no power, there’s no point asking which setting it is on. So that question comes first, and its message tells someone exactly what to check.

The colors work like a traffic light: red means stop and fix it, yellow means look at it. light = light.worse(Light.RED) keeps the worse of the current color and red. If every question is false, the final else reports how many tags the camera can see. The ? : at the very end is a one-line if that picks “tag” or “tags”.
