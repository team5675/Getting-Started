Simulation Lab 6 of 7

Detect stale data and recover

You will prove: detect, inhibit and recover.

Before you start

Keep working in the same sim-starter folder, with your edits from Lab 5. Lost your work, or starting on a different computer? Stop the simulator and copy checkpoint 06 first; how checkpoints work shows which two files go where.

Do this lab in one sitting if you can. Save a backup before you change anything.

Make the edit

Your edit: Read health checks and enums/state choices. Complete heartbeatIsStale. The input is an elapsed age in seconds, not a count of periodic calls.

return ageSeconds > 0.50;

Run and observe

In Teleop, move slowly, then check Pause simulated sensor heartbeat. Keep this browser window focused. The sensor age grows. After it exceeds 0.50 seconds, the real WPILib Alert becomes active, the station displays its warning and applied speed becomes zero. The Alert is also published through NetworkTables under Training for compatible viewers.

Try the boundary

Uncheck the fault: fresh data clears the Alert and held movement input resumes. Release movement before recovering if you want to remain still. Record the experiment and compare input, requested speed, applied speed, heartbeat age, AlertActive and Reason. During a stale fault in Teleop, held movement still appears as requested speed while applied speed is zero. Releasing the key clears the request. In Autonomous a stale fault cancels the auto rather than pretending to pause a timed trajectory; disable and start a fresh run after recovery. Exactly 0.50 is not stale under this rule; 0.501 is. Browser disconnect is a different failure: its watchdog disables the simulated Driver Station and requires a fresh mode selection.

Connection to the 2027 practice code

SystemHealthCheck on the real practice bot checks fresh readings, not merely whether a Java hardware object was constructed. A healthy constructor cannot prove a camera heartbeat or gyro update is arriving. Reviewed source map.

Your turn · Change a fault rule

In a separate saved experiment, choose a different positive stale threshold. Predict its alert time, measure it with timestamps, and restore 0.50 for the final checks.

Write the behavior you intend before typing. Save your experiment separately from the reference checkpoint.

Save your evidence

Write your prediction, observation and explanation. Save a backup or Git checkpoint when ready. Compare with answers/06 only after trying.

A reset experiment

After a successful Lab 4 run, disable and drive to a different position on your next Teleop run. Disable again. Compare TrainingLine.auto with Reset Odometry checked and unchecked, restarting Java after each edit. With it unchecked, the robot keeps its initial estimate; the path still uses the same field coordinates. Restore the checkbox before final checks.

Check the completed project

After all six labs, run:

.\robot test -PcheckStudent --rerun-tasks

This checks your current StudentProgram and path through an actual robot lifecycle, including release, interruption, slow mode, diagonal input, stale data, path reset, repeat runs and cancellation. An unfinished checkpoint should fail these final checks. The ordinary test command uses the supplied completed reference instead; it checks the starter’s infrastructure. Neither mode changes your own Java or PathPlanner files.
