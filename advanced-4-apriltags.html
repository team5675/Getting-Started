TEAM TIP

A picture is an observation.

A camera can give useful position information, but an observation is not automatically correct. Look for the conditions that make a measurement worth using.

1. What the camera actually sees

Odometry drifts because it never looks at the field. A camera can. FRC fields have AprilTags: square black-and-white codes, a bit like QR codes, each with an ID number. The organizers publish a field map that lists exactly where every tag is.

The camera finds a tag’s four corners in its picture, measured in pixels. From where those corners land, and the tag’s known size, it works out where the tag is compared with the camera. Then, because the field map says where the tag is on the field, it can work backward to where the camera, and so the robot, must be.

2. Three things must be right

That backward calculation uses three pieces of information that people measure. If any one is wrong, the robot ends up in the wrong place, very confidently.

WhatThe question it answersHow the team gets itWhat a mistake looks like
Lens calibration (“intrinsics”)Which direction does each pixel look in?A ChArUco calibration of that exact cameraErrors that change across the picture and with distance
Camera mount (“extrinsics”)Where is the camera on the robot, and which way does it point?Measure it; enter it in the code or the camera’s settingsA systematic error that can rotate with the robot’s heading. Angle effects depend on the solver and can grow with distance (section 6)

A fourth thing happens while the robot runs: the timing of each picture and the trust in the robot’s heading. Advanced 5 and 6 cover those.

3. Calibrating the lens with a ChArUco board

Every lens bends light a little, most at the edges of the picture, and every camera’s sensor sits slightly differently. A lens calibration measures this for one physical camera. A calibration from another camera of the same model is not a substitute.

The tool is a ChArUco board: a chessboard whose white squares hold small ArUco markers. Chessboard corners can be located very precisely. The markers tell the software which corner it is looking at, even when part of the board is out of view.

  • The board must be flat. Fix a print to something rigid. Measure the square and marker sizes with calipers and type in the measured values, not the sizes you meant to print.
  • Take varied pictures. Limelight’s guide asks for at least 25 snapshots to start, building to about 50. Fill the whole picture, including the edges and corners, and tilt the board so many views are at an angle.
  • Read the score. The reprojection error is the average gap, in pixels, between predicted and detected corners. Limelight’s guide calls under 1 pixel good, with 0.3–0.8 typical. It also reports a pixel aspect ratio, which should be close to 1.00 (0.99–1.01).
A wrinkled board and a good-looking score

A bent or wrinkled board teaches the camera the wrong lens, and the team’s old board is wrinkled. Use a fresh, flat print for any new calibration or check, and keep the old calibration files for comparison. And remember: a low score only says the model fits the pictures it was made from. Advanced 8 shows how to check it with new pictures.

The Limelight calibration guide describes hardware-zoom and 5-megapixel exceptions. Confirm the active model and pipeline on the installed firmware. Choosing a file alone is not proof that a particular pipeline uses it.

4. Where is the camera on the robot?

The camera mount is a transform from the robot’s center to the camera: how far forward (x), left (y) and up (z), and how it is turned (roll, pitch, yaw). In WPILib’s convention, a positive pitch tips the camera’s front down. This is WPILib’s forward/left/up convention. A camera UI or raw API may label its sideways axis or angles differently; verify the installed tool’s convention and the robot’s adapter before entering mount values.

A tape measure gives the position. The angles are harder: a camera that is 2° off looks perfectly straight. The next two sections show why those 2° matter.

5. From a tag to the robot

We will do in 2D what the camera does in 3D. You know where the tag is on the field. The camera tells you where the tag is compared with the camera. Work backward twice: tag → camera, then camera → robot center.

Where this goes: in Robot.java in your practice project, add the imports at the top. Replace only practice(), and add the helper method printPose below it.

Code to use: imports

import edu.wpi.first.math.geometry.Pose2d;
import edu.wpi.first.math.geometry.Rotation2d;
import edu.wpi.first.math.geometry.Transform2d;
import edu.wpi.first.math.geometry.Translation2d;

Code to use: practice()

private void practice() {
    // A tag on the field (made-up place): x 8.0, y 4.0, facing back toward x = 0
    Pose2d tagOnField = new Pose2d(8.0, 4.0, Rotation2d.fromDegrees(180));

    // Where the camera sits on the robot: 0.30 m in front of the center, facing forward
    Transform2d robotToCamera = new Transform2d(0.30, 0.0, Rotation2d.kZero);

    // What the camera measured: the tag is 3.0 m ahead, 0.5 m to the left, facing the camera
    Transform2d cameraToTag = new Transform2d(3.0, 0.5, Rotation2d.fromDegrees(180));

    // Work backward: from the tag to the camera, then from the camera to the robot's center
    Pose2d cameraOnField = tagOnField.transformBy(cameraToTag.inverse());
    Pose2d robotOnField = cameraOnField.transformBy(robotToCamera.inverse());

    printPose("Camera", cameraOnField);
    printPose("Robot ", robotOnField);
}

Code to use: new helper method, below practice

private void printPose(String label, Pose2d pose) {
    System.out.println(label + ": x=" + String.format("%.2f", pose.getX())
        + " y=" + String.format("%.2f", pose.getY())
        + " heading=" + String.format("%.1f", pose.getRotation().getDegrees()));
}

inverse() turns a move around: if cameraToTag goes from the camera to the tag, its inverse goes from the tag back to the camera. Starting at the tag and applying it lands on the camera. The second step does the same with the mount.

Run the new version: save with Ctrl+S, stop the previous simulation, then type .\robot. Watch the VS Code Terminal. These startup examples run while the simulator is disabled. No robot, controller or camera is needed.

6. A camera that’s turned 2° the wrong way

Now suppose the camera was bumped. It really points 2° to the left, but the code still thinks it points straight ahead. We will compare two simplified 2D calculations: one estimates heading from a tag, and one fixes heading to a gyro value. They illustrate a difference relevant to MegaTag1 and MegaTag2, but they are not Limelight’s image solver. Real results also depend on 3D geometry, tag corners, calibration and firmware.

MegaTag1 trusts the tags for everything: x, y and heading. Replace practice() with this version (keep printPose):

Code to use: practice(), MegaTag1 style

private void practice() {
    Pose2d tagOnField = new Pose2d(8.0, 4.0, Rotation2d.fromDegrees(180));
    Pose2d realRobot = new Pose2d(4.70, 3.50, Rotation2d.kZero);
    Rotation2d gyroHeading = Rotation2d.kZero; // the gyro is right

    Transform2d realMount = new Transform2d(0.30, 0.0, Rotation2d.fromDegrees(2)); // really turned 2 degrees left
    Transform2d codeMount = new Transform2d(0.30, 0.0, Rotation2d.kZero);          // what the code was told

    // What the real camera measures, from where it REALLY points
    Pose2d realCamera = realRobot.transformBy(realMount);
    Transform2d cameraToTag = new Transform2d(realCamera, tagOnField);

    // MegaTag1 style: the whole pose (x, y AND heading) comes from the tag
    Pose2d estimate = tagOnField.transformBy(cameraToTag.inverse()).transformBy(codeMount.inverse());

    printPose("Real robot", realRobot);
    printPose("Estimate  ", estimate);
    double error = estimate.getTranslation().getDistance(realRobot.getTranslation());
    System.out.println("Position error: " + String.format("%.3f", error) + " m");
}

Expected output — read this; do not paste it into Java

Real robot: x=4.70 y=3.50 heading=0.0
Estimate  : x=4.70 y=3.49 heading=2.0
Position error: 0.010 m

The position is almost right, but the heading is 2° off: the camera’s mistake became the robot’s heading. MegaTag2 takes the heading from the gyro instead and lets the tag decide only x and y. Replace only the // MegaTag1 style comment and the Pose2d estimate = ...; statement with the following block. Keep the printPose and error-printing lines below it:

Code to use: replace the MegaTag1 block

    // MegaTag2 style: the heading comes from the gyro; the tag only gives x and y
    Rotation2d cameraHeading = gyroHeading.plus(codeMount.getRotation());
    Translation2d tagFromCamera = cameraToTag.getTranslation().rotateBy(cameraHeading);
    Translation2d cameraPosition = tagOnField.getTranslation().minus(tagFromCamera);
    Pose2d estimate = new Pose2d(cameraPosition, cameraHeading).transformBy(codeMount.inverse());

Estimate  : x=4.68 y=3.61 heading=0.0

Now the heading is right, but the robot is 11 cm off sideways. Change realRobot’s x from 4.70 to 1.70, so the camera is about 6 m from the tag, and run again:

Expected output — read this; do not paste it into Java

Real robot: x=1.70 y=3.50 heading=0.0
Estimate  : x=1.69 y=3.71 heading=0.0

An angle mistake doesn’t disappear; it moves somewhere else. A position mistake in the mount is different: tell the code the camera is at 0.25 m instead of 0.30 m and every estimate is 5 cm off, near or far. That difference is a useful clue when a camera’s answers look wrong.

For the curious: what happens on the practice bot, which uses both

The practice bot seeds its heading from MegaTag1 while disabled, then uses MegaTag2 corrections. In this simplified model, seeding from the misconfigured camera makes the heading 2° wrong and largely hides the position error in the following calculation. A real Limelight is not guaranteed to cancel errors this way. The important lesson is that a plausible dashboard position cannot independently validate the heading or camera mount. Try it: set gyroHeading to Rotation2d.fromDegrees(2) in the MegaTag2 version. The far case drops to about 1 cm, and the heading prints as 2.0. Only an independent check, like a tape measure, catches it.
