How checkpoints work

The source project starts at Lab 1. Keep your completed edits as you progress. If you need a fresh starting point, stop the simulator and copy the two files from checkpoints/NN: StudentProgram.java goes into src/main/java/frc/robot, and TrainingLine.path goes into src/main/deploy/pathplanner/paths. For example, checkpoint 03 contains the completed behavior from Labs 1–2 with the Lab 3 TODO remaining.

Matching answers/NN files are for comparison after trying. Follow the backup steps before replacing your own work, or make a Git checkpoint if you have learned Git. Checkpoint files outside src do not compile automatically. Every source checkpoint builds; its unfinished behavior is intentional.

Simulation checkpoint 01

1. Bind an input to your command

Your edit: Open src/main/java/frc/robot/StudentProgram.java. In StudentProgram.configure replace the Lab 1 TODO with this binding. The supplied driver.a() gives you a Trigger: an object that checks whether that input is pressed. Keep the supplied driver/input helpers as they are. Today you only connect this Trigger to the existing light command; writing lambdas is not part of this task.

// A Trigger asks this question repeatedly. whileTrue starts on a press,
// and cancels on release. Our command's end() performs the cleanup.
robot.driver.a().whileTrue(robot.lightCommand());

Run and observe

Start the program, choose Teleop, click the keyboard area and hold Space. The indicator turns on; releasing Space turns it off. Holding the on-screen Light button does the same. Click Disabled while holding it; cleanup still runs. Re-enable with the input released before pressing again.

Try the boundary

Temporarily add .withTimeout(1.0) to the command passed to whileTrue. Hold for two seconds: it finishes after one second and does not restart until you release and press again. Restore the original binding. “While true” describes trigger edges; it is not an endless restart loop.

Connection to the 2027 practice code

The 2027 driver’s A-button brake binding uses whileTrue too. The light owns a light requirement; a drive brake owns the drivetrain requirement. Reviewed source map.

Simulation checkpoint 02

2. Drive with a default command

Your edit: After the controller lesson, add this line in configure, below your light binding. A default command runs whenever its subsystem is free. Open RobotContainer.manualDriveCommand and follow its runEnd action into TrainingDrive.driveFieldRelative.

// A default command runs when this subsystem has no other command.
// The supplied helper reads current input on each scheduler pass.
robot.drive.setDefaultCommand(robot.manualDriveCommand());

Run and observe

Use Teleop. Hold D for about one second: the robot moves right and X increases by about one meter. W moves up (+Y), A left (−X), and S down (−Y), matching your screen. Reset only while Disabled. Repeat with D and Shift held: the same time produces about 0.35 meters. Try A as well. Release all controls and check that requested speed becomes zero.

Try the boundary

Hold W and D together. The total translation speed stays at 1 m/s, not 1.41, because the XY vector is normalized together. Change Constants.SLOW_MODE_SCALE from 0.35 to 0.20, rerun and explain the result; restore 0.35 before the final student checks. A path later interrupts this default command by requiring the drive subsystem.

Connection to the 2027 practice code

The real bot uses a named SLOW_MODE_SCALE constant and a drivetrain default command. Scaling both signs of an input matters: reverse must slow down too. Reviewed source map.

Simulation checkpoint 03

3. Record your own experiment

Your edit: After debugging and logs, complete StudentProgram.record with the following named signals. Logger writes values; println is a readable message but is not a substitute for numeric telemetry. These calls run repeatedly, after the model updates.

Logger.recordOutput("Training/InputX", robot.input().x());
Logger.recordOutput("Training/SlowMode", robot.input().slow());
Logger.recordOutput("Training/XMeters", robot.drive.getPose().getX());
Logger.recordOutput("Training/YMeters", robot.drive.getPose().getY());
Logger.recordOutput("Training/HeadingDegrees", robot.drive.getPose().getRotation().getDegrees());
var request = robot.drive.getRequestedSpeeds();
Logger.recordOutput("Training/RequestedSpeedMps", Math.hypot(request.vxMetersPerSecond, request.vyMetersPerSecond));

Run and observe

At home: AdvantageScope. Launch AdvantageScope from the WPILib tools, choose File → Open Log and select the newest .wpilog. Search the sidebar for Training (it may be under RealOutputs). Drag RequestedSpeedMps and AppliedSpeedMps to a Line Graph tab, then add SlowMode. Zoom to your experiment and read timestamps in seconds. This uses the viewer included with WPILib; no separately supplied team file is needed.

Guided session with the locally supplied v11 viewer

In v11, open Topic explorer, search Training/, and click Load topic beside each signal you need. Then choose its A or B graph button. These custom topics are listed at first but loaded on demand; zero retained values before loading does not mean the robot failed to record them.

Record five seconds disabled, normal forward motion, slow forward motion, release, then Disable. Stop Java with Ctrl+C. Find the newest .wpilog under this project’s logs folder. Open it in AdvantageScope, or use v11 when your mentor has supplied its local file. The v11 viewer itself is kept local and is not bundled into this website.

Try the boundary

Select Training/SlowMode, Training/RequestedSpeedMps, Training/AppliedSpeedMps and Training/XMeters. AdvantageKit may show them below RealOutputs. Find the moment slow mode changed using timestamps. Compare displacement over equal time intervals, not an assumed sample count. If a topic is missing, check its exact spelling and whether you restarted the edited program. Label requested and applied values separately; in this ideal model they normally match, but a fault will separate them.

Connection to the 2027 practice code

The real drivetrain records Drive/Pose and Drive/OdometryOnlyPose. Those are two estimates, not ground truth. Your simpler scalar X/Y signals make the first log easier to inspect. Reviewed source map.

Simulation checkpoint 04

4. Connect AutoBuilder and run a path

Your edit: Finish pose and the PathPlanner editor lab. In configure, add the callback wiring below. Read method references first. getPose reports field coordinates; the speed callbacks use robot-relative velocities. The supplied trainingPathConfig contains fictional model dimensions.

// All speed callbacks below use ROBOT-relative velocities.
// Pose remains in the fixed BLUE field frame.
AutoBuilder.configure(
        robot.drive::getPose,
        robot.drive::resetPose,
        robot.drive::getRobotRelativeSpeeds,
        (speeds, feedforwards) -> robot.drive.driveRobotRelative(speeds),
        new PPHolonomicDriveController(new PIDConstants(5, 0, 0), new PIDConstants(5, 0, 0)),
        robot.trainingPathConfig(),
        () -> false, // No alliance mirroring on this classroom grid.
        robot.drive);
// Our ideal velocity model does not use wheel feedforward voltages.
robot.markPathConfigured();

Run and observe

Use PathPlanner GUI 2026.1.2 and open this robot project’s root folder (the folder containing build.gradle) as described in the editor lab. Inspect TrainingLine: start (1,1), end (2,1), heading 0°, max speed 0.5 m/s. Leave the supplied path unchanged for this first run. Open TrainingLine.auto too: Reset Odometry is checked. The simulator loads this auto at startup; restart Java after editing it. Start Java, select TrainingLine in the station’s autonomous selector, then Autonomous. Expect the reset to (1,1), movement to about (2,1), then zero applied speed. The Java library loads the actual .path file.

Try the boundary

Disable, move in Teleop to an unexpected position, disable again and repeat Autonomous. It resets and follows the same path. Disable mid-path on a third run; it must stop. The classroom example intentionally keeps the fixed blue frame on both alliances. Real field mirroring and driver perspective are separate topics; do not add an alliance heading flip here.

Connection to the 2027 practice code

The real AutoRoutines connects PathPlanner to drivetrain callbacks and resets the starting pose. This model omits wheel dynamics, feedforward application and real odometry sensors, so its result does not validate real swerve tuning. Reviewed source map.

Simulation checkpoint 05

5. Add a fresh command at a path marker

Your edit: Add this registration in configure. It runs during startup before any path is loaded. Commands.defer supplies a new action for each use. The declared requirement is light, so the marker does not compete with the path for the drive subsystem.

// Register BEFORE loading an auto/path. Defer constructs a fresh action
// on each use, and declares exactly the returned command's requirements.
NamedCommands.registerCommand("Checkpoint", Commands.defer(
        () -> robot.lightCommand().withTimeout(0.4)
                .beforeStarting(robot::eventReached), Set.of(robot.light)));

Run and observe

In PathPlanner, add an event marker to TrainingLine at waypoint-relative position 0.5, named Checkpoint. Give it a Named Command action also named Checkpoint, and save. For the first two-waypoint segment, 0.5 is halfway through the segment parameter, not a promise about elapsed time. If the editor controls are unfamiliar, compare the complete answers/05/TrainingLine.path file after trying.

Try the boundary

Run Autonomous twice, with Disabled between runs. The station’s event count increases once per run; the light flashes for 0.4 seconds while the robot continues driving. Interrupt during the event and confirm the light turns off. Misspelling the name or registering after loading the path can leave an event missing; check the Terminal.

Connection to the 2027 practice code

The practice robot registers LogMarker using Commands.defer(() -> Commands.print("[Auto] LogMarker reached"), Set.of()). Your event adds a subsystem requirement and cleanup to that same factory idea. Reviewed source map.

Simulation checkpoint 06

6. Detect stale data and recover

Your edit: Read health checks and enums/state choices. Complete heartbeatIsStale. The input is an elapsed age in seconds, not a count of periodic calls.

return ageSeconds > 0.50;

Run and observe

In Teleop, move slowly, then check Pause simulated sensor heartbeat. Keep this browser window focused. The sensor age grows. After it exceeds 0.50 seconds, the real WPILib Alert becomes active, the station displays its warning and applied speed becomes zero. The Alert is also published through NetworkTables under Training for compatible viewers.

Try the boundary

Uncheck the fault: fresh data clears the Alert and held movement input resumes. Release movement before recovering if you want to remain still. Record the experiment and compare input, requested speed, applied speed, heartbeat age, AlertActive and Reason. During a stale fault in Teleop, held movement still appears as requested speed while applied speed is zero. Releasing the key clears the request. In Autonomous a stale fault cancels the auto rather than pretending to pause a timed trajectory; disable and start a fresh run after recovery. Exactly 0.50 is not stale under this rule; 0.501 is. Browser disconnect is a different failure: its watchdog disables the simulated Driver Station and requires a fresh mode selection.

Connection to the 2027 practice code

SystemHealthCheck on the real practice bot checks fresh readings, not merely whether a Java hardware object was constructed. A healthy constructor cannot prove a camera heartbeat or gyro update is arriving. Reviewed source map.

Check the completed project

After all six labs, run:

.\gradlew.bat test -PcheckStudent --rerun-tasks

This checks your current StudentProgram and path through an actual robot lifecycle, including release, interruption, slow mode, diagonal input, stale data, path reset, repeat runs and cancellation. An unfinished checkpoint should fail these final checks. The ordinary test command uses the supplied completed reference instead; it checks the starter’s infrastructure. Both modes run from a test-owned deploy copy under build/simulation-test. Neither mode overwrites your source or PathPlanner files.
