Aiming in field coordinates

FieldPointAim does one generic thing: while the driver keeps translating, it continuously rotates the robot to face a chosen point on the field. When the 2027 game is revealed, "the point" becomes the goal / feeder / whatever — the pattern doesn't change.

Later reference: Field-coordinate aiming

Use it with a mentor when the topic becomes relevant. The team-project activities need a separate, tested training repository; SystemCore work uses its own bench setup.

One physical point, one field heading

In the 2026 baseline, express both the robot position and the target point in the blue-alliance field frame. At the same robot pose, facing the same physical point needs the same heading regardless of alliance.

Rotation2d headingToTarget = targetPoint.minus(robotPose.getTranslation()).getAngle();

minus gives the displacement from robot to target. getAngle() gives its direction. This is a geometry excerpt; the existing aim helper supplies the surrounding control code.

Keep joystick direction separate

The driver may expect forward stick to mean away from their alliance wall. That is operator-relative translation. The target heading above is field-relative. Set the swerve request's target-direction perspective to BlueAlliance using the starter's pinned Phoenix API so an operator-perspective rotation is not also applied to this heading.

The rule to remember Do not add your own red-alliance 180° offset to a blue-frame target heading. Selecting an alliance-specific target point is a separate decision about where to aim.
Check your understanding In simulation, hold the robot pose and target fixed. Predict the heading on blue and red. Then test both. Explain separately what happens to joystick translation when alliance changes.
