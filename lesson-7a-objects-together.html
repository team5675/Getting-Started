1. See it: give an object starting values

In Lesson 7 every new Counter() started at 0. Many objects need starting values instead. A battery has a name written on it and a first voltage reading. A constructor can take parameters, just like a method, so you hand those values over when you make the object.

static class Battery {
    private final String label;
    private double lowestVolts;

    Battery(String label, double firstReading) {
        this.label = label;
        this.lowestVolts = firstReading;
    }

    String getLabel() { return label; }
    double getLowestVolts() { return lowestVolts; }
}

// Inside main:
Battery spare = new Battery("Spare", 12.6);
Battery match = new Battery("Match", 12.8);
System.out.println(spare.getLabel() + " " + spare.getLowestVolts());
System.out.println(match.getLabel() + " " + match.getLowestVolts());
PAUSE & PREDICT

One recipe, two batteries

Predict the two printed lines before you read on. Which values went into which object?

It prints Spare 12.6, then Match 12.8. Each new Battery(...) runs the constructor once, with that call’s values.

Two things called label. Inside the constructor there is a parameter named label: the text you passed in, which exists only while the constructor runs. There is also the object’s field named label, which the object keeps for as long as it exists. A plain label means the closest one, the parameter. this.label means “this object’s field”. So this.label = label; reads: copy the label I was given into my own field.

final means “set once”. private final String label; must get its value in the constructor, and no later line may change it. If one tries, Java refuses to compile. Use final for things that should never be swapped out after the object is made: a battery’s label, or the battery an alarm watches. lowestVolts is not final, because a new low reading replaces it.

2. See it: one object uses another

An object can also be a constructor’s parameter. Below, a button is given the light it controls. It keeps that light in a final field and switches it on when pressed.

static class Light {
    private boolean on = false;
    void setOn(boolean value) { on = value; }
    boolean isOn() { return on; }
}

static class LightButton {
    private final Light light;

    LightButton(Light light) {
        this.light = light;
    }

    void press() { light.setOn(true); }
}

// Inside main:
Light light = new Light();
LightButton button = new LightButton(light);
System.out.println(light.isOn());
button.press();
System.out.println(light.isOn());
PAUSE & PREDICT

The button never mentions main’s light

button.press() uses the button’s light field to turn on the shared Light object. Predict both printed lines. Explain why main sees the change even though the button’s reference stays the same.

It prints false, then true. new LightButton(light) does not copy the light. It hands over a reference to the same object. Like the optional “one object, two names” experiment in Lesson 7, main’s variable and the button’s field are two name tags on one Light object. The button’s light field is final and never changes: it points at the same Light the whole time. final stops a field from being pointed at a different object. It does not freeze the object itself, so that Light can still switch on.

Open the file with Ctrl+P. Save after every change with Ctrl+S, then run it in the Terminal opened in home-java-starter:

Before you change anything it prints null lowest 0.0 V, readings 0 twice, with Spare alarm: false after each. null means “no text here yet”: the constructor never stored the label.

  1. Fix the Battery constructor. The line label = label; copies the parameter onto itself and changes nothing. Make it this.label = label;. Then store firstReading in this.lowestVolts, and set this.readingCount to 1. Save and run. ✔ Spare lowest 12.6 V, readings 1 on both report lines, because record does nothing yet.
  2. Finish record(volts). Add 1 to readingCount. Then, if volts is lower than lowestVolts, store volts in lowestVolts. Run. ✔ The second report line is now Spare lowest 11.3 V, readings 2.
  3. Finish the LowBatteryAlarm constructor. Remember the battery it was given: this.battery = battery;. Do this before the next step.
  4. Finish isSounding(). Return whether the battery’s lowest reading is below the limit: return battery.getLowestVolts() < LIMIT_VOLTS;. Run. ✔ The last Spare alarm line is now true.
  5. Make two fields final. Change private String label; to private final String label;, and the alarm’s private Battery battery; to private final Battery battery;. Run: the output does not change. Robot glimpse · one idea to notice

Your alarm keeps the battery it was given. In Lesson 8, a robot command keeps the part of the robot it controls, called a subsystem, in the same way.

Optional: see the command you will meet in Lesson 8

This is from the simulation starter you download at the robot project step. You are not expected to explain extends Command or addRequirements yet; Lesson 8 covers them. Do not paste this into your Java exercise.

Reading example from src/main/java/frc/robot/commands/KeepLightOn.java in the simulation starter — do not paste

public class KeepLightOn extends Command {
    private final PracticeLight light;
    public KeepLightOn(PracticeLight light) {
        this.light = light;
        addRequirements(light); // Another light command must interrupt this one.
    }
    @Override public void initialize() { light.setOn(true); }
    @Override public void end(boolean interrupted) { light.setOn(false); }
}

Where the one light is handed over, in RobotContainer.java — do not paste

public final PracticeLight light = new PracticeLight();
public Command lightCommand() { return new KeepLightOn(light); }

Find the same parts as in your alarm: a private final field, a constructor parameter with the same name, this.light = light;, and one object created once and handed to the command. When the command calls light.setOn(true), it changes that same PracticeLight, just as your alarm reads that same Battery.
