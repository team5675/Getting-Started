1. Put the robot somewhere you have measured

One tape measurement gives one distance, but a pose needs three numbers: x, y and heading. A simple jig gives all three: two contact pads against a rigid chassis face, and one stop on a perpendicular face.

The jig itself must be placed from field features you trust, and you must know the offset from the contact faces to the robot’s center. A robot pressed square against a rail on the carpet is placed repeatably, but that alone doesn’t say where on the field it is.

How precise is the heading? If one pad can be off by 5 mm more than the other, the heading is uncertain by atan(5 ÷ spacing). The farther apart the pads, the better.

Where this goes: in Robot.java in your simulation starter, replace only practice().

Code to use

private void practice() {
    double gapMm = 5.0;      // how far one contact point can be off, compared with the other
    double sightlineM = 4.0; // how far away the tags are
    double[] spacingsMm = {375.0, 750.0, 1000.0};
    for (double spacing : spacingsMm) {
        double headingDeg = Math.toDegrees(Math.atan(gapMm / spacing));
        double sidewaysMm = sightlineM * 1000.0 * Math.tan(Math.toRadians(headingDeg));
        System.out.println("Contacts " + spacing + " mm apart: heading +/-"
            + String.format("%.2f", headingDeg) + " degrees, at 4 m that is +/-"
            + String.format("%.0f", sidewaysMm) + " mm");
    }
}

Run the new version: save with Ctrl+S, stop the previous simulation, then type .\robot. Watch the VS Code Terminal. These startup examples run while the simulator is disabled. No robot, controller or camera is needed.

Expected output — read this; do not paste it into Java

Contacts 375.0 mm apart: heading +/-0.76 degrees, at 4 m that is +/-53 mm
Contacts 750.0 mm apart: heading +/-0.38 degrees, at 4 m that is +/-27 mm
Contacts 1000.0 mm apart: heading +/-0.29 degrees, at 4 m that is +/-20 mm

A third of a degree sounds tiny, but 4 m away it is about 27 mm sideways. That is the same size as the camera mistakes you are trying to find. Spread the contacts as far apart as the chassis allows.

2. Where the scatter number comes from

Advanced 8’s scatter helper returns the standard deviation. Here it is by hand, for the same three readings as Advanced 8’s table: 2.03, 2.04 and 2.02 m, whose average is 2.03 m.

Reading (m)Minus the average (m)Squared (m²)
2.030.000.0000
2.04+0.010.0001
2.02−0.010.0001
Sum of the squares0.0002
  1. Square each difference. Squaring makes every difference positive, so a reading above the average and one below it cannot cancel out.
  2. Divide by one less than the count. 0.0002 ÷ (3 − 1) = 0.0001. Using one less than the count corrects for measuring the differences from the readings’ own average; with many readings it hardly matters.
  3. Take the square root. √0.0001 = 0.01 m. The square root brings the answer back to meters.

So a typical reading sits about 1 cm from the average, which is what Advanced 8’s “check the hand table” run printed. The same steps, written out with loops instead of a helper, compute both numbers for ten readings:

Where this goes: replace only practice().

Code to use

private void practice() {
    double referenceX = 2.000; // measured with the jig and a tape measure
    double[] cameraX = {2.031, 2.027, 2.035, 2.029, 2.033, 2.030, 2.028, 2.034, 2.032, 2.031};

    double sum = 0.0;
    for (double x : cameraX) {
        sum = sum + x;
    }
    double average = sum / cameraX.length;

    double sumOfSquares = 0.0;
    for (double x : cameraX) {
        sumOfSquares = sumOfSquares + (x - average) * (x - average);
    }
    double scatter = Math.sqrt(sumOfSquares / (cameraX.length - 1));

    System.out.println("Bias:    " + String.format("%+.4f", average - referenceX) + " m");
    System.out.println("Scatter: " + String.format("%.4f", scatter) + " m");
}

Expected output — read this; do not paste it into Java

Bias:    +0.0310 m
Scatter: 0.0026 m

The first loop is the average; the second adds up the squared differences; the last line divides by one less than the count and takes the square root. Advanced 8’s helpers do exactly this.

3. Investigate, then prove it on a station you didn’t tune

A bias is a clue, not a diagnosis. Measure at least two stations, A and B, with different positions, headings and distances, and look for a pattern:

What repeatsLook at first
One camera is off at many stationsThat camera’s mount, lens calibration, focus, and whether it is the camera you think it is
Several cameras are off near one tagThat tag’s place in the field map, and the reference survey
The error changes a lot with headingThe mount angles, the offset to the robot’s center, the heading reference (Advanced 4, section 6)
The error changes across the picture or with distanceThe lens model, mount/heading angles, tag size and solve geometry; distance alone does not identify the cause
Big scatter with no steady biasMotion, blur, lighting, blocked tags, or timing (Advanced 6)
The result changes when the robot is placed againThe jig and the reference, not the camera

Then try a small correction that makes physical sense, such as a mount angle a mechanic could believe. Try it offline on the recorded data. A real fix improves several stations, not just one. Finally, test it at a third station, C, which you did not use while choosing the correction. If C fails, the correction was wrong, however good A looked. Never change the mount, the lens and the field map all at once to make one view look right.

4. Checking the lens calibration the right way

Advanced 4 said a low reprojection score only proves the model fits its own pictures. To check a lens calibration honestly:

  1. Keep the existing lens model fixed. Don’t recalibrate. Save the old calibration files first.
  2. Take 15–25 new pictures of a flat, measured ChArUco board, covering the center, edges and corners at several tilts and distances. Keep them separate from any calibration set.
  3. Estimate the board pose in each new image while holding the lens model fixed, then compare projected and detected corners. Do not refit the lens model on these check images. Look at the misses by region of the picture, not only one average. Errors that grow toward the edges point to the lens model.
  4. Check a real distance. Measure the camera’s answer to a correctly sized tag at a few known distances, measured from a defined point on the camera.

If the old model fails, make a new calibration from a different set of pictures and compare both on the same held-out pictures. A lower fitting score alone is not a reason to switch.

5. The practice bot’s recorder and workbench

In the real robot · 2027Practice

The practice bot has a built-in recorder for this check. Its timing is a few named constants, each with a comment:

Reading example from src/main/java/frc/robot/Constants.java — do not paste

/** Seconds the robot must hold still before recording starts. */
public static final double SETTLE_S = 0.5;

/** Seconds of camera frames to record once settled. */
public static final double CAPTURE_S = 2.0;

/** Seconds from D-pad Up until the capture gives up and reports FAILED. */
public static final double ATTEMPT_TIMEOUT_S = 6.0;

And how many pictures make a capture — do not paste

/** Fewest qualified multi-tag frames for a COMPLETE capture. */
public static final int MIN_FRAMES = 10;

With the robot disabled at a measured station, the operator presses D-pad Up. The robot pauses normal vision, waits until it has been still for half a second, then records camera frames for two seconds. A capture needs at least 10 frames that each see two or more tags, and gives up after 6 seconds. D-pad Down leaves the check, and the robot then needs a fresh MegaTag1 fix (Advanced 5). The saved session opens in an offline workbench in a web browser, where small mount changes can be tried on the recorded data. “COMPLETE” means enough data was recorded. It does not mean the camera passed.

From the team’s 2027 practice-bot code (repository 2027Practice, October 2026). It is built with the 2027 test version of WPILib, so a few names differ from your 2026 tools. Read it; don’t paste it.

Optional · with a mentor

The team also has an offline workbench for this check that opens in a web browser. It is not one of this website’s downloads, so you do not need it to finish this page. If your mentor shows it to you, try a correction on its made-up example and compare two stations: a wrong correction can improve one, both or neither, so success on one station alone is not enough.

For mentors

The workbench is src/main/deploy/verification/index.html in the private 2027Practice repository; open it in a normal web browser. Choose Load synthetic example, then try the known correction: X +3 cm, Y −1 cm, Z −2 cm, roll −1°, pitch +2°, yaw +4°. Both made-up stations drop to almost zero error. This workbench changes saved MT1 transforms; it does not rerun the camera’s image solver, validate lens intrinsics or faithfully recompute MT2. Its pitch is positive nose-down, the WPILib convention. The numbers are made up for teaching; they are not the team’s cameras.

6. Try it with sliders: the pose lab

The pose lab runs in this browser with nothing to install. Move sliders to see what a camera mount mistake, a trust setting or a late picture does to the robot’s idea of where it is. It goes with Advanced 4, 5 and 6, and makes a good review after this page.

Pause and check

Work out the standard deviation of 1.99, 2.00 and 2.01 m by hand. Then explain why a correction must be tested at a station that was not used to choose it.

Compare your answer

The average is 2.00. The differences are −0.01, 0.00 and +0.01; their squares add up to 0.0002; 0.0002 ÷ 2 = 0.0001; √0.0001 = 0.01 m. A correction chosen to fix stations A and B can fit their particular mistakes without being right; only a station it never saw can show that.
