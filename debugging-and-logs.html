Today’s small goal

Find a logic error, then distinguish a live value from a recorded history. Prerequisites: loops and arrays. Allow 30–45 minutes. The Java exercise is independent of the optional robot-log activity.

1. A successful compile is the first check

A compile error means Java could not translate your source. A runtime error happens while it runs, such as reading an array outside its bounds. A logic error produces a result that does not match your intention. All three are ordinary parts of learning.

Open Debugging.java in the home starter. Predict its total for {2, 3, 4}. The intended answer is 9. Run it: the starter prints 7. Read the loop slowly; it begins at index 1, so it misses the first value.

2. Watch the program take one step

  1. In VS Code, open Debugging.java. Click the margin to the left of total += values[i];. A red dot marks a breakpoint: a place to pause.
  2. In the stable 2026 editor, choose Debug above main when the Java extension has loaded. Alpha 7 may disable Run/Debug CodeLens; use the trace-table alternative below in that editor. Choose this file if prompted. If it cannot find Java, use the Java extension’s runtime configuration to select the installed JDK path from the home guide.
  3. When execution pauses, add i, values[i], and total to Watch, or inspect them in Variables.
  4. Use Step Over (usually F10). Watch total change. The breakpoint line has not run yet when execution first stops there.
  5. Stop debugging, change the initial index to 0, save, and repeat. Then run the file with check. Explain the single-element and empty-array results too.
Debug does not appear

You can finish the same investigation with a trace table: columns for i, values[i], and total before/after. Or temporarily print them inside the loop, run, and remove the extra print after fixing the bug. The terminal source-file command in the home guide does not depend on CodeLens.

3. A robot needs a history

A console message is useful for Hello World. For robot values that change every loop, named logs let us compare what happened over time. AdvantageKit records values; AdvantageScope displays a saved log or live telemetry; Elastic is the driver’s dashboard.

Reading excerpt from the practice bot — do not paste into the plain Java download

Logger.recordOutput("Drive/Pose", state.Pose);
Logger.recordOutput("Drive/OdometryOnlyPose", odometryOnlyPose);

These lines in CommandSwerveDrivetrain record the corrected pose and the wheels/gyro-only estimate. Compare them at the same time. A gap is evidence to investigate, not proof that the camera or wheels are right.

4. Begin with five real state changes

Try the E3 log-reading lesson and small download. It uses recorded 2026 robot data, has a worksheet and answers, and needs no robot tools. Then use a complete mentor-provided log and the AdvantageScope line-graph guide. The following keys belong to the current practice robot; the historical sample uses different names. The team’s Unified WPILOG Analyzer is another teaching tool, with clock, topic and match-window fixes still required before general student use.

  1. Open the supplied WPILOG. Write down the robot commit, date, units and what the team did.
  2. Graph Drive/VelocityX_mps and locate a known stop. Does speed approach zero? Then inspect Vision/<camera>/AcceptedCount: a flat cumulative count means no new corrections were accepted.
  3. Drag a pose into an appropriate field view, and compare the two pose traces. Do not put meters, amps and degrees on one unlabeled axis.
  4. Write a claim with an interval and evidence: “From time A to B, accepted count stayed unchanged while the camera heartbeat continued.” Ask what other signal would test your explanation.

Find the topics by their suffix: AdvantageKit receiver prefixes can differ for live and saved data. A successful unit test is not a successful simulation session. The reviewed alpha robot has a known native-library startup issue; use a mentor-provided saved log until full simulation is verified.
