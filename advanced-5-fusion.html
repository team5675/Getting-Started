PAUSE & PREDICT

Two witnesses. One estimate.

Odometry says 5.00 m; the camera says 5.40 m. With the example’s camera share of 0.25, which way should the estimate move—and how far?

1. Two imperfect witnesses

Odometry (wheels + gyro)Camera (AprilTags)
UpdatesEvery loop, smoothlyOnly when a tag is in view
Short-termVery goodJumpy: each fix is a little different
Long-termDrifts and never recovers (Advanced 3)Doesn’t drift
Can be badly wrong whenWheels slip, the robot is bumped or carriedA tag is far away, blurred or ambiguous, or a calibration is off

Neither one is good enough alone. A pose estimator keeps odometry running all the time and nudges it toward each camera fix by an amount that depends on how much it trusts each one.

2. Trust as a number

Trust is written as a standard deviation: roughly, “how far off this usually is.” A small number means trusted, and a big number means not trusted. In the example below, odometry gets 0.1 m. A camera fix from far away might be 1.0 m, a close one with two tags 0.3 m.

For this straight-line example with unchanged heading, WPILib 2026’s pose estimator applies this gain to the position error. It uses configured process and measurement standard deviations; this is not a general formula for averaging any two measurements:

share = odometry std dev ÷ (odometry std dev + camera std dev)
Here: 0.1 ÷ (0.1 + 0.3) = 0.25, so the estimate moves a quarter of the way, from 5.00 to 5.10.

import edu.wpi.first.math.kinematics.SwerveModulePosition;

Code to use: practice()

private void practice() {
    SwerveDriveKinematics kinematics = new SwerveDriveKinematics(
        new Translation2d(0.3048, 0.3048), new Translation2d(0.3048, -0.3048),
        new Translation2d(-0.3048, 0.3048), new Translation2d(-0.3048, -0.3048));
    SwerveModulePosition[] wheels = {
        new SwerveModulePosition(), new SwerveModulePosition(),
        new SwerveModulePosition(), new SwerveModulePosition()};

    SwerveDrivePoseEstimator estimator = new SwerveDrivePoseEstimator(
        kinematics, Rotation2d.kZero, wheels,
        new Pose2d(5.00, 2.00, Rotation2d.kZero),  // where odometry thinks the robot is
        VecBuilder.fill(0.1, 0.1, 0.1),            // trust in odometry (meters, meters, radians)
        VecBuilder.fill(0.3, 0.3, 9_999_999));     // trust in the camera; its heading is ignored

    Pose2d cameraSays = new Pose2d(5.40, 2.00, Rotation2d.kZero);
    double time = 0.0;
    for (int i = 1; i <= 5; i++) {
        time = time + 0.02;                                       // one robot loop later
        estimator.updateWithTime(time, Rotation2d.kZero, wheels); // the wheels haven't moved
        estimator.addVisionMeasurement(cameraSays, time);
        System.out.println("After camera fix " + i + ": x = "
            + String.format("%.3f", estimator.getEstimatedPosition().getX()));
    }
}
PieceWhat it does here
SwerveDrivePoseEstimatorOdometry plus camera blending in one object. The real drivetrain has one inside it.
VecBuilder.fill(0.1, 0.1, 0.1)Three trust numbers: x, y and heading.
9_999_999A huge std dev for heading: “never let the camera change the heading.” Underscores make big numbers readable; Java ignores them.
updateWithTime(...)One odometry update, as the real robot does every loop. The wheels report no movement here.
addVisionMeasurement(cameraSays, time)One camera fix, with the time the picture was taken (Advanced 6).

4. Not every picture deserves a vote

Trust numbers handle ordinary noise. Some fixes are simply wrong, and blending even a quarter of a wrong answer moves the robot. So the vision code throws those away first. The practice bot’s rules:

Throw the fix away if…Why
the camera isn’t answering, or is on the wrong pipelineOld or meaningless numbers
no tag is in viewThere is no pose to use
the picture’s time is impossibleToo old to help, or a clock problem (Advanced 6)
the pose is off the field, beyond a 25 cm marginPhysically impossible. In 2026 this check had a bug: it skipped one wall and its margin pointed inward, so good fixes near a wall were thrown away
the robot is spinning faster than half a turn per secondBlurred pictures, and the heading sent to MegaTag2 is already stale
the tags are far away on averageSmall tags in the picture give poor answers
only one tag is seen and it is ambiguous (MegaTag1)It could be the mirror-image pose

Good fixes then get a trust number from the robot’s formula: farther tags mean a bigger std dev, and more tags a smaller one. That’s the xyStdDevMeters method from the Lesson 5 real-robot box.

5. Seed, then maintain

The practice bot uses its two camera answers (Advanced 4) in two steps:

  1. Seed with MegaTag1, only while disabled and still. A seed resets x, y and heading to an accepted camera estimate. The current seed guard checks disabled state and turning rate; it does not prove zero translational motion. Keep the robot stationary for this operation. The separate reference-capture tool has additional wheel-speed checks.
  2. Maintain with MegaTag2 while driving. It nudges x and y using the blending above, and never touches the heading. The heading comes from the gyro after field alignment. Its data must stay fresh and trustworthy; alignment alone does not protect against a reset or fault.

So the robot needs to remember one important fact: is my heading lined up with the field? If it isn’t, MegaTag2 must stay off, because MegaTag2 is only as good as the heading it is given.

6. A real bug, and the fix

Until October 2026, one true-or-false value meant two things: “the heading is trusted” and “we still want a fresh MegaTag1 fix.” Every disable set it to false, so a disable both asked for a fresh fix and took away trust. Now follow a match:

  1. Before the match the robot is disabled, sees tags and seeds. Trusted.
  2. Autonomous runs. Trusted.
  3. Between auto and teleop the robot is disabled for a few seconds. Trust is taken away, and a fresh fix is needed. But if no tag is in view during those few seconds, there is no fix.
  4. Teleop starts. Seeding is only allowed while disabled, so the robot can’t seed again, and MegaTag2 stays off for the whole of teleop.

The fix split the one value into two separate facts, headingTrusted and refreshWanted. A disable now only sets refreshWanted. The gyro keeps measuring through a disable, so there is no reason to doubt the heading. Trust is taken away only when something really overwrites or questions it.

Discuss: what else should make the robot stop trusting its heading?

Today trust is taken away by the X button, the View button (“this way is forward”), and starting or leaving a reference check. A code review in October 2026 pointed out another case that isn’t handled yet: the gyro itself restarting or being reset while the robot code keeps running. Then its heading is no longer lined up with the field. How could the code notice that? What should the Pre-Match tab say when it happens? This is a real open question for the team.

Reading example from src/main/java/frc/robot/subsystems/vision/VisionSubsystem.java — do not paste

static String seedRejectReason(PoseObservation obs, boolean connected, boolean pipelineCorrect,
    boolean disabled, double now, double requestedAt, double omegaRadPerSec) {
  if (!disabled) {
    return "robot is enabled (MegaTag1 only seeds while disabled)";
  }
  if (!connected) {
    return "camera not connected (no heartbeat)";
  }
  if (!pipelineCorrect) {
    return "camera is not on its AprilTag pipeline";
  }
  if (obs == null) {
    return "no AprilTag in view";
  }
  // ... time stamp, distance, field, turning and ambiguity rules ...
  return null;
}

And what happens on every disable, in RobotContainer.java — do not paste

public void onDisabled() {
  // Every disable is a chance to refresh the pose from a fresh MegaTag1 fix (2026 production
  // behavior), BUT we keep trusting the current heading while we wait. In a match the robot is
  // disabled for only a few seconds between auto and teleop; if no tag is in view then, clearing
  // the seed here would switch vision off for all of teleop. (Before Oct 2026 this called
  // clearPoseSeed(). See PoseSeedTracker for the full story.)
  vision.requestFreshSeed();
}

The first excerpt is the Lesson 4 pattern again: worst problem first, one answer. The second is the October 2026 fix: one call, with a comment explaining why. A disable asks for a fresh fix, but doesn’t take away trust.
